# Spring AI

---

## AI 서비스를 담는 백엔드 개발

> 직접 REST API를 호출할 수도 있지만, 서비스가 커지고 AI를 활용하려고 설계하려면? **Spring AI!**

### Spring의 검증된 구조에 생성형 ai 개발로 확장하려면?

기존 방식을 버리고 새로운 기능을 추가하는게 아닌, 필요한 기능을 ai가 사용할 수 있도록 연결하는 방식으로 한다.

### 어떤 이점이 있는가?

- 모델별 인증·요청·응답 처리
- 스트리밍과 구조화된 출력 처리
- RAG, Memory, Tool Calling 구현
- 토큰 사용량과 호출 시간 관측
- 모델 교체와 테스트
- 기존 서비스·DB·보안 체계와의 연결

Spring AI는 ChatModel, ChatClient, Advisor, VectorStore, @Tool 같은 방식으로 연결해서 사용한다.

## 1. Spring AI를 쓰는 이유

작성한 답:

> 기존 Java/Spring 환경에서 AI 서비스를 연결하기 위해 사용한다.

정확합니다. 여기에 “왜 직접 API를 호출하지 않는가?”까지 붙이면 더 좋은 답이 됩니다.

> Spring AI는 기존 Java/Spring의 서비스·데이터·보안·운영 체계를 유지하면서 LLM, RAG, Tool Calling 같은 AI 기능을 일관된 방식으로 연결하기 위해 사용한다.

현업에서는 단순히 LLM을 호출하는 것보다 다음이 중요합니다.

- 기존 `Service`와 `Repository` 재사용
- Spring Security의 인증·권한 적용
- 모델 호출과 토큰 사용량 관측
- 모델별 API 차이 격리
- RAG와 Tool Calling의 공통 처리

### 2. Spring Data와 비슷한 점

공통점은 **서로 다른 구현체를 공통 인터페이스로 추상화한다는 것**입니다.

```text
Spring Data
JPA / MongoDB / Redis
        ↓
Repository라는 공통 사용 방식

Spring AI
OpenAI / Anthropic / Gemini / Ollama
        ↓
ChatModel이라는 공통 사용 방식
```

덕분에 비즈니스 코드는 특정 벤더의 HTTP 요청 형식에 덜 의존합니다.

다만 “아무 수정 없이 완전히 교체 가능하다”는 뜻은 아닙니다. 모델마다 성능과 지원 기능이 다르기 때문에 재검증은 필요합니다.

### 3. 모델 교체 시 재검증할 것

토큰 비용·지연시간·오류는 모두 맞는 답입니다. 다만 이것들은 주로 **운영 품질**에 해당합니다.

모델 교체 시에는 두 영역을 함께 확인해야 합니다.

| 영역        | 확인할 내용                                          |
| ----------- | ---------------------------------------------------- |
| 응답 품질   | 정확성, 환각, 한국어 품질, 기존 프롬프트 호환성      |
| 기능 호환성 | Tool Calling, Structured Output, 스트리밍, 옵션 지원 |
| 운영 품질   | 비용, 지연시간, 오류율, 요청 제한                    |
| 제약 조건   | 컨텍스트 길이, 데이터 보관 정책, 보안 정책           |

가장 중요한 것은 **컴파일이 성공해도 AI 서비스의 품질은 달라질 수 있다**는 점입니다.

### 4. 연결하고 싶은 기능

아이디어 자체는 좋은데, `챗봇`, `RAG`, `Tool`, `MCP`의 역할을 구분하면 설계가 선명해집니다.

```text
사내 챗봇
 ├─ RAG: 사내 규정과 문서를 찾아 답변
 ├─ Tool: 휴가 잔여일 조회, 회의실 예약 등 실제 기능 실행
 └─ MCP: 이런 외부 도구를 표준 방식으로 연결
```

“기존 데이터를 RAG로 구조화한다”보다는 다음 표현이 정확합니다.

> 사내 문서를 분할하고 임베딩하여 Vector Store에 저장한 뒤, 질문과 관련된 문서를 검색해 LLM의 답변 근거로 제공한다.

RAG는 **지식을 조회**하고, Tool은 **행동을 수행**합니다.

예를 들면:

- “육아휴직 규정을 알려줘” → RAG
- “내 휴가가 며칠 남았어?” → 사내 인사 시스템 조회 Tool
- “다음 주 월요일 휴가를 신청해줘” → 휴가 신청 Tool
- 여러 사내 시스템의 Tool을 표준으로 연결 → MCP

현업에서는 조회용 Tool부터 시작하는 편이 안전합니다. 신청·삭제·결제처럼 상태를 변경하는 Tool에는 사용자 확인, 권한 검사, 감사 로그가 반드시 필요합니다. 교본 역시 Spring AI의 핵심을 기업 데이터와 API를 AI 모델에 연결하는 것으로 설명합니다.

## 기억할 핵심

```text
Spring AI = 기존 Spring 시스템과 AI를 연결하는 통합 계층
추상화 = 모델 차이를 제거하는 것이 아니라 격리하는 것
RAG = 지식 조회
Tool = 행동 수행
MCP = Tool 연결의 표준
```

### 동기 비동기

- 요청을 처리하는 방법을 분리해서
- 비동기 : 응답을 기다리지 않고 전달할 때 요청할때 어떻게 해야하는지(함수)까지 함께 던져놓고 응답이 발생하면 처리함 -> 던지기만 하면 됨 -> 멀티 스레드
- 동기 : 요청이 오면 기다리다가 응답을 함 (함수를 던지는게 아닌 기다리고 응답받아서 보냄)
