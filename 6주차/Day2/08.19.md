## 1. sLLM이란?

sLLM(Small Language Model)은 대형 LLM보다 파라미터와 연산량이 적은 언어 모델입니다.

단순히 성능이 낮은 모델이 아니라, 다음과 같은 상황에 맞춘 **작고 효율적인 전용 모델**에 가깝습니다.

- 정해진 업무를 대량으로 반복할 때
- 빠른 응답이 필요할 때
- GPU와 운영비를 줄여야 할 때
- 데이터를 외부 API로 보내기 어려울 때
- 인터넷이 없는 내부망·기기에서 실행해야 할 때
- 모델의 버전과 응답 정책을 직접 통제해야 할 때

대표적인 용도는 문서 분류, 정보 추출, 태깅, 정형화된 요약, 고객 문의 분류, 도구 호출 등입니다.

반대로 자유로운 대화, 복잡한 추론, 다양한 주제 처리가 중요하다면 대형 LLM이 더 적합할 수 있습니다.

> 핵심 판단: 모든 문제에 작은 모델이 필요한 것도 아니지만, 모든 문제에 가장 큰 모델이 필요한 것도 아니다.

---

## 2. sLLM의 주요 활용 방식

### 반복 업무 자동화

입력과 출력 형식이 정해진 작업을 빠르고 저렴하게 처리합니다.

- 고객 상담 유형 분류
- 문서에서 핵심 항목 추출
- 제품·품목 코드 분류
- 리뷰 분석 및 태깅
- 정해진 형식의 요약

### 특정 분야 전문화

범용 능력 일부를 포기하고 특정 업무의 정확도와 일관성을 높입니다.

- 의료 기록 요약
- 금융 상담 분류
- 법률 문서 처리
- 농업·제품 규정 질의응답

### 온디바이스·내부망 실행

모델을 클라우드가 아닌 PC, 스마트폰, 공장 설비 또는 사내 서버에서 실행합니다.

- 민감정보 보호
- 네트워크 없이 사용
- 응답 지연 감소
- 외부 서비스 의존성 감소

### AI Agent의 전문 모델

하나의 거대 모델이 모든 일을 처리하지 않고, 작업별 모델을 조합합니다.

- 분류 → 분류용 sLLM
- 정보 추출 → 추출용 sLLM
- API 호출 → Function Calling용 sLLM
- 복잡한 추론 → 대형 LLM

## 3. 모델 선택 방법

모델은 유명세나 최신 여부보다 **업무와 실행 환경에 맞는지**가 중요합니다.

### 모델 계열

대표적인 Open-weight 모델 계열은 다음과 같습니다.

- Llama: 범용성이 높고 생태계와 도구가 풍부함
- Qwen: 다양한 크기, 다국어·코딩·추론 모델 제공
- Gemma: 경량 실행과 온디바이스 활용에 적합
- Phi: 적은 파라미터로 높은 효율을 지향

### 모델 크기

모델이 커지면 일반적으로 처리 능력도 높아지지만 다음 비용이 증가합니다.

- GPU 메모리
- 추론 시간
- 학습 비용
- 운영 비용

따라서 **목표 성능을 만족하는 가장 작은 모델**부터 검토하는 것이 좋습니다.

### Base 모델과 Instruct 모델

- Base 모델: 다음 단어 예측을 중심으로 사전학습된 원형 모델
- Instruct 모델: 질문, 명령, 대화에 잘 반응하도록 추가 학습된 모델

일반적인 대화, SFT, 업무 특화에는 Instruct 모델을 먼저 검토합니다.
대규모 도메인 원문을 계속 학습시키려면 Base 모델도 고려합니다.

### Model Card 확인 항목

Hugging Face 등에서 모델을 선택할 때 다음을 확인합니다.

- 공식 개발사가 배포한 모델인지
- 텍스트·이미지 등 어떤 입력을 지원하는지
- 모델 크기와 Base/Instruct 구분
- Transformers, PEFT, 양자화 지원 여부
- 공개된 평가 결과
- 상업적 사용 가능 여부
- 수정·재배포 조건

특히 **Open-weight라고 해서 아무 제한 없이 사용할 수 있다는 뜻은 아닙니다.**

## 4. Prompt, RAG, Fine-Tuning의 차이

세 기술은 해결하려는 문제가 다릅니다.

| 부족한 것          | 우선 검토   | 역할                           |
| ------------------ | ----------- | ------------------------------ |
| 지시나 문맥        | Prompt      | 요청할 때 규칙과 예시 제공     |
| 외부·최신 정보    | RAG         | 관련 문서를 검색해 모델에 제공 |
| 반복되는 업무 행동 | Fine-Tuning | 원하는 처리 방식 자체를 학습   |

간단히 구분하면 다음과 같습니다.

- 지식이 자주 바뀐다 → RAG
- 답변 형식과 행동을 고정하고 싶다 → Fine-Tuning
- 간단한 지시만 필요하다 → Prompt

예를 들어 최신 대출금리를 답해야 한다면 RAG가 적합합니다. 금리가 바뀔 때마다 모델을 다시 학습할 필요가 없기 때문입니다.

반면 고객을 `정상/관심/이탈위험`으로 안정적으로 분류해야 한다면 Fine-Tuning이 적합합니다.

> 지식은 RAG, 행동은 Fine-Tuning으로 생각하면 이해하기 쉽습니다.

## 5. Transformer가 문맥을 이해하는 방식

### 토큰 처리 흐름

모델 내부에서는 문장이 다음 순서로 처리됩니다.

1. 문장을 토큰으로 나눔
2. 토큰을 숫자 ID로 변환
3. ID를 벡터로 변환
4. Transformer가 토큰 사이의 관계를 계산
5. 다음 토큰의 확률을 출력

### Self-Attention

Self-Attention은 각 토큰이 문장의 다른 토큰을 얼마나 참고해야 하는지 계산하는 기능입니다.

- Query: 내가 어떤 정보를 찾는가
- Key: 내가 참고 대상이 될 만한 정보인가
- Value: 실제로 전달할 정보

Query와 Key를 비교해 중요도를 구하고, 그 중요도만큼 Value를 섞어 문맥이 반영된 표현을 만듭니다.

복잡한 수식보다 다음처럼 이해하면 됩니다.

> Attention은 문장 안에서 “현재 단어가 어떤 단어를 얼마나 참고할지” 결정하는 기능이다.

### Causal Mask

텍스트 생성 모델은 다음 단어를 예측할 때 미래 단어를 미리 보면 안 됩니다.

Causal Mask는 현재 위치보다 뒤에 있는 토큰을 보지 못하게 막습니다. 따라서 모델은 이전까지의 내용만 보고 다음 토큰을 예측합니다.

### 긴 문맥의 비용

토큰 수가 두 배가 되면 Attention이 계산할 관계는 약 네 배가 됩니다.

즉, 문맥이 길어질수록 메모리와 계산량이 빠르게 증가합니다. 긴 문서를 무조건 통째로 넣는 방식이 비효율적인 이유입니다.

## 6. LLM이 학습하는 과정

LLM 학습은 다음 과정을 반복합니다.

1. 텍스트를 토큰으로 변환
2. 이전 토큰을 보고 다음 토큰의 확률을 예측
3. 실제 정답 토큰과 비교
4. 오차인 Loss 계산
5. 오차가 줄어들도록 파라미터 수정
6. 여러 데이터와 Epoch에 걸쳐 반복

### Cross-Entropy Loss

모델이 정답 토큰에 높은 확률을 주면 Loss가 작아지고, 낮은 확률을 주면 Loss가 커집니다.

수식 자체보다 기능적으로는 다음 의미입니다.

> 모델이 정답을 얼마나 확신했는지를 점수로 바꾸고, 틀린 정도가 큰 파라미터를 더 많이 수정한다.

### 학습과 실제 생성의 차이

학습할 때는 정답 문장이 있으므로 이전 위치에 실제 정답 토큰을 넣어줄 수 있습니다. 이를 Teacher Forcing이라고 합니다.

실제 생성에서는 정답이 없으므로 모델이 방금 생성한 토큰을 다음 입력으로 사용합니다. 따라서 초반에 잘못 생성하면 그 오류가 뒤의 문맥에도 영향을 줄 수 있습니다.

## 7. Fine-Tuning이란?

Fine-Tuning은 이미 언어 능력을 가진 모델에 추가 데이터를 학습시켜 **특정 업무와 행동에 적응시키는 과정**입니다.

처음부터 모델을 만드는 것이 아니라 기존 능력을 활용하므로 Pre-training보다 데이터와 비용이 적게 듭니다.

Fine-Tuning이 필요한 대표적인 경우는 다음과 같습니다.

- 특정 분류·요약·추출 성능이 부족함
- 출력 형식과 문체가 일정하지 않음
- 전문 분야의 용어나 문서 구조에 익숙하지 않음
- 긴 프롬프트를 매 요청마다 넣어야 함
- 작은 모델로 특정 업무의 실용적인 성능을 확보하고 싶음

Fine-Tuning 전략은 두 가지 질문으로 설계합니다.

1. 무엇을 학습시킬 것인가?
2. 모델의 어느 파라미터를 수정할 것인가?

## 8. 무엇을 학습시킬 것인가?

### Continued Pre-training

도메인의 원문을 추가로 학습합니다.

- 데이터: 금융 보고서, 의료 논문, 법률 문서, 소스 코드 등
- 학습 대상: 전문 용어, 표현 방식, 문서 구조, 개념 관계
- 적합한 경우: 모델이 해당 분야의 언어 자체에 익숙하지 않을 때

질문·답변 데이터를 만드는 것이 아니라 원문으로 다음 토큰 예측 학습을 계속합니다.

### Supervised Fine-Tuning(SFT)

입력과 모범 답변을 짝으로 만들어 학습합니다.

- 질문에 답하는 방식
- 분류·요약·추출 절차
- 출력 형식
- 말투와 답변 길이
- 조직의 업무 처리 방식

일반적인 업무 특화에서 가장 직접적으로 사용하는 방법입니다.

### Preference Alignment

같은 질문에 대한 여러 답변 중 어느 답변이 더 좋은지 학습합니다.

- 더 유용한 답변
- 더 정확하고 명확한 답변
- 안전한 답변
- 불필요하게 장황하지 않은 답변
- 조직 정책과 일치하는 답변

보통 SFT 이후 응답 품질을 추가로 다듬는 단계입니다.

## 9. 파라미터를 어떻게 수정할 것인가?

### Full Fine-Tuning

모델의 모든 파라미터를 수정합니다.

장점:

- 모델을 폭넓게 변화시킬 수 있음
- 충분한 데이터와 자원이 있다면 높은 성능 가능

단점:

- GPU 메모리와 학습 비용이 큼
- 목적별로 전체 모델을 저장해야 함
- 데이터가 부족하면 기존 능력을 잃을 수 있음

최고 성능이 중요하거나 모델의 내부 표현을 크게 바꿔야 할 때 사용합니다.

### PEFT

대부분의 기존 파라미터를 고정하고 작은 일부만 학습합니다.

장점:

- 학습 메모리와 시간이 적음
- 작은 Adapter만 저장하면 됨
- 하나의 Base 모델에 여러 업무용 Adapter를 교체 가능
- 반복 실험과 업데이트가 쉬움

제한된 GPU에서 sLLM을 튜닝할 때 실용적인 기본 선택입니다.

## 10. LoRA

LoRA는 대표적인 PEFT 방식입니다.

기존 모델 가중치는 그대로 고정하고, 업무에 필요한 **작은 변화량만 두 개의 작은 행렬로 나누어 학습**합니다.

기능적인 핵심은 다음과 같습니다.

- 전체 모델을 수정하지 않음
- 학습해야 할 파라미터 수가 크게 감소
- Adapter 파일만 별도로 저장 가능
- 업무별 Adapter를 교체해 사용할 수 있음

### 주요 설정

- `r`: 학습할 변화의 표현 범위
- `lora_alpha`: 학습된 변화가 원래 모델에 반영되는 강도
- `target_modules`: LoRA를 적용할 모델 내부 모듈
- `lora_dropout`: 과적합을 줄이기 위한 설정

`r`이 커지면 표현력과 학습량이 함께 증가합니다. 무조건 크게 설정하기보다 작은 값부터 검증하는 것이 좋습니다.

자료에서 제시하는 일반적인 출발점은 다음과 같습니다.

- `r=16`
- `lora_alpha=32`
- `lora_dropout=0.05~0.1`
- `bias="none"`
- `task_type="CAUSAL_LM"`

이 값은 정답이 아니라 실험 시작점입니다.

## 11. Quantization과 QLoRA

### Quantization

모델 가중치를 더 적은 비트로 표현해 메모리를 줄이는 기술입니다.

대략적인 10억 개 가중치의 저장 공간은 다음과 같습니다.

- FP32: 약 4GB
- FP16: 약 2GB
- INT8: 약 1GB
- 4-bit: 약 0.5GB

비트 수를 줄이면 메모리는 절약되지만 원래 값과 근사값 사이에 오차가 생길 수 있습니다.

### QLoRA

QLoRA는 다음 두 기술을 결합합니다.

- Base 모델 → 4-bit로 양자화해 메모리 절약
- 학습 부분 → LoRA Adapter만 학습

즉, **모델은 작게 저장하고 실제 학습량도 작게 유지하는 방식**입니다.

일반적인 설정은 다음과 같습니다.

- 4-bit 로드 활성화
- `nf4` 양자화 사용
- Double Quantization 활성화
- 최신 GPU는 `bfloat16`, 일부 구형 GPU는 `float16` 연산

제한된 GPU로 비교적 큰 모델을 튜닝할 때 유용합니다.

## 12. Fine-Tuning 문제와 해결 방법

### 데이터 품질 문제

증상:

- 잘못된 답변과 형식 반복
- 특정 클래스만 과도하게 출력
- 실제 입력에서는 성능 저하

대응:

- 틀린 정답 제거
- 중복 데이터 제거
- 출력 형식 통일
- 클래스와 상황을 균형 있게 구성
- 실제 서비스 입력과 예외 사례 포함

많은 데이터보다 **정확하고 일관된 데이터**가 중요합니다.

### 과적합

증상:

- 학습 데이터에는 잘 답하지만 새로운 표현에는 실패
- Train Loss는 감소하지만 Validation Loss는 증가
- 학습 문장을 그대로 암기

대응:

- Epoch 축소
- Early Stopping
- 다양한 데이터 추가
- Train/Validation 데이터 분리

### 학습 불안정

증상:

- Loss가 크게 흔들리거나 증가
- NaN 발생
- 실행마다 결과 차이가 큼

대응:

- Learning Rate 낮추기
- Batch Size와 Gradient Accumulation 조정
- 수치 정밀도 설정 확인

### Catastrophic Forgetting

새로운 업무를 학습하면서 기존의 일반 지식·추론·지시 수행 능력이 약해지는 현상입니다.

대응:

- Learning Rate 낮추기
- Epoch 줄이기
- 일반 데이터 일부 혼합
- Full Fine-Tuning 대신 PEFT 검토

### Hallucination

Fine-Tuning을 했다고 사실 정확성이 자동으로 좋아지지는 않습니다. 모델은 잘못된 정보도 자신 있게 말할 수 있습니다.

대응:

- 정확한 학습 데이터 사용
- 모르면 답변을 유보하는 예시 포함
- 최신·외부 정보는 RAG로 제공
- 별도의 사실 검증 단계 적용

---

## 13. 실무 체크리스트

### 학습 전

- Fine-Tuning으로 해결할 문제인지 확인
- 목표 행동과 평가 기준 정의
- Base 모델 결과 저장
- 데이터의 정답·형식·문체 점검
- 중복 제거
- 실제 입력과 예외 사례 포함
- Train/Validation 데이터 분리

### 학습 중

- Train Loss와 Validation Loss 함께 확인
- Validation Loss가 증가하는지 확인
- Learning Rate와 Epoch가 과도하지 않은지 점검
- Loss 진동과 NaN 확인
- 중간 Checkpoint 저장
- 실제 출력 예시를 정기적으로 확인

### 학습 후

- Base 모델보다 목표 업무가 개선됐는지 비교
- 학습하지 않은 표현에도 대응하는지 평가
- 기존 일반 능력이 유지되는지 확인
- 도메인 밖 질문에 억지로 답하지 않는지 확인
- 환각과 편향을 별도로 평가

## 최종 핵심 정리

1. sLLM은 대형 LLM의 축소판이 아니라 특정 업무에 최적화하는 효율적인 모델이다.
2. 반복량, 비용, 속도, 보안, 실행 환경을 기준으로 sLLM 사용 여부를 결정한다.
3. 최신 지식은 RAG, 반복되는 행동과 출력 방식은 Fine-Tuning이 적합하다.
4. Fine-Tuning은 `학습 목적`과 `파라미터 수정 방식`의 조합으로 설계한다.
5. 일반적인 업무 특화는 Instruct 모델에 SFT를 적용하는 방식부터 검토한다.
6. 제한된 GPU에서는 LoRA 또는 QLoRA가 실용적인 기본 선택이다.
7. 성능은 데이터 양보다 데이터의 정확성·일관성·다양성에 크게 좌우된다.
8. Train Loss만 낮다고 성공한 것이 아니며, 새로운 입력과 기존 능력까지 함께 평가해야 한다.
