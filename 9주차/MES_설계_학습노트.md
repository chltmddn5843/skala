# PartFlow 설계 전에 알아야 할 지식과 판단 기준

기준일: 2026-09-08. 이번 프로젝트의 최소 흐름인 `작업지시 → LOT 생산실적 → 치수검사 → 관련 LOT 조회 → 메모 요약`을 설계하기 위한 학습 노트다. 실제 기업의 MES 전체 기능이나 산업별 품질 규정을 다루지 않는다.

## 1. 가장 먼저 구분할 개념

### 기준정보와 발생정보

- **기준정보(Master Data)**: 여러 업무에서 반복해 참조하는 비교적 안정된 정보. 품목, 설비, 검사규격, 사용자 등.
- **발생정보(Transaction/Event Data)**: 실제 업무를 수행하며 계속 생기는 기록. 작업지시, LOT 생산실적, 검사, 측정값 등.

판단 질문: `이 값이 바뀌면 과거 기록까지 바뀌어야 하는가?`

예를 들어 BR-A의 검사규격을 덮어쓰면 과거 측정값의 판정 근거가 사라진다. 따라서 규격은 버전을 새로 만들고 LOT이 사용한 규격 버전을 참조하도록 한다.

### 계획과 실적

- 작업지시는 생산할 품목·목표수량·납기라는 **계획**이다.
- LOT은 실제로 어떤 설비에서 언제 얼마나 생산했는지 나타내는 **실적 묶음**이다.

판단 질문: `예정했던 값인가, 실제로 발생한 값인가?`

목표수량은 작업지시에, 실제 생산수량은 LOT에 둔다. 진행률은 연결된 LOT 생산수량 합계 ÷ 작업지시 목표수량으로 계산한다.

### 상태와 사실

상태 컬럼은 편리하지만 다른 기록에서 계산 가능한 상태를 중복 저장하면 서로 어긋날 수 있다.

- 작업지시의 `대기/진행/종료`는 명시적인 업무 상태이므로 저장한다.
- LOT 검사 상태는 검사 기록 존재 여부로 계산할 수 있으므로 별도 저장하지 않는 기본안을 사용한다.
- `부적합 여부`는 측정값과 당시 규격으로 서버가 판정한다.

판단 질문: `이 상태를 바꾸는 명확한 업무 행위가 있는가, 다른 데이터에서 확실히 계산할 수 있는가?`

## 2. 작업지시와 LOT 설계

### 관계

이번 모델은 `품목 1:N 작업지시`, `작업지시 1:N LOT`이다. 작업지시 하나를 여러 번 나눠 생산할 수 있기 때문이다.

예:

- WO-001: BR-A 10개 생산
- LOT-A: WO-001로 M1에서 5개 생산
- LOT-B: WO-001로 M1에서 5개 생산

이번 범위에서는 LOT 하나가 작업지시 여러 개나 품목 여러 개를 섞지 않는다.

### LOT 경계를 정하는 기준

LOT은 단순 번호가 아니라 같은 조건으로 관리할 생산 묶음이다. 실제 현장에서는 원자재·설비·교대·공정 조건 등에 따라 달라질 수 있다. 이번 프로젝트에서는 다음으로 단순화한다.

- 같은 작업지시
- 같은 품목
- 같은 설비
- 한 번의 연속된 생산 시작~종료

판단 질문: `문제가 생겼을 때 함께 확인해야 할 최소 생산 묶음은 무엇인가?`

### 식별자

- DB 내부 PK `id`: 관계 연결용.
- 업무 식별자 `order_no`, `lot_no`: 화면·검색·대화에서 사용하는 번호.
- 업무 번호는 의미를 너무 많이 넣지 않고 고유성을 보장한다.

날짜·설비·품목은 별도 컬럼에 있으므로 LOT 번호 문자열을 잘라 업무 데이터를 복원하지 않는다.

## 3. 시간과 관련 LOT 조회

생산 시점 하나만 저장하면 일부가 겹치는 생산을 찾기 어렵다. LOT에는 `started_at`, `ended_at`을 저장한다.

조회 구간 `[from, to)`와 LOT 생산 구간 `[started_at, ended_at)`이 겹치는 조건:

`started_at < to AND ended_at > from`

시작은 포함하고 끝은 제외하면 09:00~09:30과 09:30~10:00을 중복된 시간으로 보지 않는다.

관련 LOT 기본 조건:

1. 기준 LOT 제외
2. 같은 품목
3. 같은 설비
4. 지정 시간 구간과 생산 시간이 겹침

판단 기준:

- 같은 설비라도 품목이 다르면 같은 품질 문제가 적용되는지 근거가 부족하므로 기본 제외한다.
- 검사 적합 LOT도 근거 비교에 도움이 되므로 숨기지 않는다.
- 검사대기 LOT은 추가 확인이 필요하므로 먼저 표시한다.
- 선정 결과는 `관련 후보`이며 불량 판정이 아니다.
- 시간 범위는 사용자가 입력한다. 근거 없이 시스템이 자동 추정하지 않는다.

## 4. 검사와 규격 설계

### 무엇을 저장할까

- 검사규격: 품목, 검사항목, 목표값, 하한, 상한, 단위, 버전.
- 검사: 어느 LOT을 누가 언제 검사했는지와 메모.
- 측정값: 검사 대상 번호, 측정값, 판정.

한 LOT 검사에 여러 측정값이 있으므로 `검사 1:N 측정값`이다.

### 판정 기준

이번 가상 규격은 9.90mm 이상 10.10mm 이하를 적합으로 본다. 경계 포함 여부를 명시해야 9.90과 10.10의 결과가 흔들리지 않는다.

판정은 서버가 한다. 프론트가 보내는 PASS/FAIL 값을 신뢰하지 않는다. 소수는 `double`의 근사 오차를 피하기 위해 Java `BigDecimal`, PostgreSQL `numeric`처럼 십진수를 정확히 다루는 타입을 사용한다.

판단 질문:

- 단위는 무엇인가?
- 소수 몇 자리까지 받는가?
- 하한·상한을 포함하는가?
- 검사수량과 측정값 개수가 일치해야 하는가?
- 판정에 사용한 규격 버전을 나중에도 찾을 수 있는가?

이번 기본안은 전수검사이며 LOT 생산수량과 측정값 개수가 같아야 확정할 수 있다.

## 5. 데이터베이스 판단 기준

### 테이블로 나눌 때

다음 중 하나면 별도 엔터티를 검토한다.

- 여러 곳에서 반복 참조한다.
- 독립적인 식별자와 생명주기가 있다.
- 한 개에 여러 개가 연결된다.
- 변경 이력을 보존해야 한다.

그래서 품목·설비·규격·작업지시·LOT·검사·측정값을 분리한다. 반면 관련 LOT 조회 결과는 기존 데이터로 다시 계산할 수 있으므로 저장하지 않는다.

### 제약조건을 둘 위치

- DB: 고유번호, FK, NOT NULL, 단순 범위처럼 항상 지켜야 할 구조적 규칙.
- 서버: 작업지시 누적 생산량, 규격 판정, 권한, 상태 전이처럼 여러 데이터와 업무 맥락이 필요한 규칙.
- 프론트: 빠른 입력 안내. 서버 검증을 대신하지 않는다.

중요한 규칙은 한 층에만 기대지 않는다. 프론트에서 막아도 API를 직접 호출할 수 있으므로 서버가 다시 검사한다.

### 원자성

검사 헤더만 저장되고 측정값 일부가 실패하면 불완전한 검사가 생긴다. 검사와 모든 측정값은 하나의 DB 트랜잭션으로 저장해 전부 성공하거나 전부 취소한다.

동시에 두 사용자가 같은 LOT을 확정할 가능성도 고려한다. LOT당 검사 한 건이라는 UNIQUE 제약과 서버의 충돌 응답을 함께 사용한다.

## 6. API 설계 판단 기준

API는 화면 버튼 목록이 아니라 한 번의 업무 행위를 표현한다.

- `POST /api/work-orders`: 작업지시 생성
- `POST /api/work-orders/{id}/lots`: 작업지시에 LOT 실적 등록
- `POST /api/lots/{id}/inspection`: 검사와 측정값 일괄 확정
- `GET /api/lots/{id}`: LOT 생산·검사 이력 조회
- `GET /api/lots/{id}/related?from=...&to=...`: 관련 LOT 후보 조회
- `POST /api/lots/{id}/summary`: 메모 요약 생성

각 API에서 판단할 항목:

1. 누가 호출할 수 있는가?
2. 클라이언트가 보낼 값과 서버가 조회·계산할 값은 무엇인가?
3. 성공 시 화면에 필요한 응답은 무엇인가?
4. 잘못된 입력, 없는 대상, 권한 부족, 중복·상태 충돌을 어떻게 구분하는가?
5. 일부만 저장될 가능성을 어떻게 막는가?

기본 오류 구분은 400 입력 오류, 401 로그인 필요, 403 권한 부족, 404 대상 없음, 409 중복·상태 충돌, 500 서버 오류다.

## 7. B2B 시스템에서 중요한 품질

이번 프로젝트 규모가 작아도 다음 성질은 유지한다.

- **추적성**: 누가, 언제, 어떤 작업지시·LOT·설비·규격으로 기록했는지 찾을 수 있다.
- **데이터 무결성**: 없는 품목·설비 참조, 중복 LOT, 잘못된 수량과 시간을 막는다.
- **판단 근거**: 관련 LOT이 왜 후보인지 조건을 보여준다.
- **권한**: 화면 버튼을 숨기는 데서 끝내지 않고 서버가 역할을 검사한다.
- **기록 보존**: 과거 규격과 확정 검사 결과를 덮어쓰지 않는다.
- **장애 분리**: AI 요약 실패가 생산·검사 기록 저장을 망가뜨리지 않는다.

기능 수보다 업무 규칙이 일관되고 기록의 근거를 설명할 수 있는지가 중요하다.

## 8. AI의 역할 경계

AI가 하지 않는 일:

- 측정값 합불 계산
- 관련 LOT 선정
- 품질 문제의 원인 확정
- 출하 승인

AI가 하는 일:

- 선택된 생산·검사 메모 요약
- 관찰 사실과 미확인 내용을 나눠 표시
- 사람이 검토할 질문 초안 생성

AI 출력에는 입력으로 사용한 기록을 연결한다. 기록에 없는 원인을 생성하면 실패한 요약이다.

## 9. 지금 알아야 할 범위와 나중 범위

지금 필수:

- 기준정보와 발생정보
- 계획과 실적
- 작업지시 1:N LOT
- LOT의 설비·생산시간
- 규격 버전과 측정값 판정
- PK/FK/UNIQUE/NOT NULL
- 상태 전이, 서버 검증, DB 트랜잭션
- 관련 LOT 조회 조건

이번 과제에서 제외:

- BOM·자재투입·재고·출하
- 공정 라우팅과 공정별 WIP
- ERP·PLC·측정기 연동
- 재작업·재검사·폐기 승인
- SPC·관리도·Cp/Cpk
- 다중 공장·교대조·설비 예방보전

## 10. 설계 완료 판단 체크리스트

- 작업지시 10개를 LOT-A 5개·LOT-B 5개로 표현할 수 있는가?
- LOT만 보고 품목·설비·생산시간·적용 규격을 찾을 수 있는가?
- 9.90/10.10 경계값을 일관되게 판정하는가?
- 규격이 바뀌어도 과거 판정 근거가 유지되는가?
- 같은 LOT 검사 중복과 부분 저장을 막는가?
- 관련 LOT 후보의 선정 이유를 설명할 수 있는가?
- 생산 종료·검사 완료·부적합을 서로 다른 개념으로 표현하는가?
- AI가 없어도 기본 MES와 품질 조회가 동작하는가?

이 체크리스트를 만족하면 DBML과 OAS 작성으로 넘어간다.
