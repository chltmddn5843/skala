# PartFlow — 기본 MES와 품질 확인의 공백

2026-09-08. 사용자 요청: MES 기본 로직은 아주 가볍게 구현하고 페인포인트를 상세하고 입체적으로 정의한다. 이 문서는 현재 기획 초점이며, 아래 현장 상황은 인터뷰로 검증된 사실이 아닌 **가상 시나리오와 검증할 문제 가설**이다. 사용자 백엔드 설계 분담은 유지한다.

## 1. 서비스가 풀 문제

**품질 담당자는 부적합이 발견된 LOT을 인수받았을 때, 무엇이 관찰됐고 누가 어디까지 확인했으며 다음에 무엇을 확인해야 하는지 다시 묻지 않고 파악하고 싶다.**

‘생산 데이터를 모은다’는 기본 MES의 역할이다. 이번 서비스의 차별점 후보는 **부적합 발견 후 확인·인수인계가 끊기는 구간을 짧게 만드는 것**이다. 불량률 감소·원인 규명·재발 방지 효과는 이번 데모만으로 입증하지 않는다.

## 2. 기본 MES 범위

사전 등록 품목·규격 → 작업지시 등록 → LOT 생산실적 등록 → 치수 검사 입력 → LOT 기록 조회.

- 한 공장·한 라인·대표 품목 하나(BR-A)·검사항목 하나(구멍 지름).
- 최소 생산 상태: 대기/진행/종료. LOT별 검사 전/완료는 별도.
- 규격과 측정값으로 서버가 규격 내/외를 계산하고 기록한다. LOT 5개 전수검사 데모는 기존 워크시트를 사용한다.
- 기본 입력 검증·역할 권한·중복 방지·규격 근거 보존은 유지한다.
- 공정 라우팅·재고·설비 연동·원자재 추적·SPC·검사 재작업·출하 처리는 이번 범위 밖이다.
- 별도 대시보드·알림 센터를 늘리지 않고 **LOT 목록과 LOT 상세**를 품질 담당자의 중심 화면으로 삼는다. 작업지시·실적·검사 입력은 기존 화면의 패널로 연결한다.

## 3. 가상의 하루: 같은 부적합을 서로 다르게 경험한다

| 시점 | 사람·상황 | 막히는 지점 | 영향 가설 |
| --- | --- | --- | --- |
| 생산 완료 | 작업자가 LOT-A 생산실적과 짧은 메모 기록 | 입력할 항목이 많으면 필요한 설명을 충분히 쓰기 부담스러움 | 기록이 짧아져 나중에 재질문이 필요 |
| 검사 | 검사자가 5개 중 2개의 지름이 규격 밖임을 확인 | 숫자만으로 발견 상황과 미확인 사항이 전달되지 않음 | 기록은 있지만 다음 행동이 모호 |
| 담당자 변경 | 다음 품질 담당자가 LOT-A 조회 | 앞사람이 보기만 했는지, 확인을 맡았는지 알 수 없음 | 중복 확인 또는 아무도 맡지 않는 공백 |
| 현황 보고 | 생산관리자가 작업지시 종료 확인 | 생산 종료·검사 완료·추가 확인 완료가 혼동될 수 있음 | 진행 상황을 잘못 해석하거나 품질팀에 반복 문의 |
| 다음 날 | 품질 담당자가 메모를 다시 확인 | 관찰 사실과 추측이 섞이고 이전 확인 결과를 찾기 어려움 | 조사 출발점을 매번 다시 정리 |

여기서 작업자에게는 입력 부담을 줄이고, 품질 담당자에게는 맥락을 충분히 제공해야 하는 긴장이 있다. 관리자는 빠른 현황을 원하지만, 부적합이 왜 발생했는지는 기록만으로 확정할 수 없다. 따라서 자유입력만 강요하거나 AI 원인 추정으로 빈칸을 메우지 않는다.

## 4. 문제별 원인·대응·검증

| ID | 문제 가설 | 원인 가설 | 이번 대응 | 확인할 방법 |
| --- | --- | --- | --- | --- |
| P1 | LOT의 검사 근거를 모으느라 화면·문서를 왕복 | 지시·실적·규격·검사가 별도 맥락으로 제시됨 | LOT 상세에 관련 기록과 사용 규격을 함께 표시 | 낯선 LOT의 부적합 대상과 기준을 찾는 데 걸린 시간·화면 이동 횟수 |
| P2 | 부적합 LOT을 아무도 맡지 않거나 중복 확인 | 검사 결과와 담당자의 확인 행위가 구분되지 않음 | 부적합 LOT ‘확인 필요’ 필터, 담당 품질자와 확인 메모 | 교대자가 담당자·현재 확인 상태를 정확히 찾는지 |
| P3 | 메모가 짧아 다음 담당자가 다시 질문 | 무엇을 적어야 하는지 기준 없음, 입력 부담 | ‘관찰한 사실’과 ‘추가 확인할 점’ 입력 안내. LOT·수량·규격 재입력 금지 | 같은 시나리오에서 추가 질문이 필요한 항목 수 |
| P4 | 생산 종료를 품질 문제 종료로 오해 | 서로 다른 상태를 ‘완료’ 한 단어로 표시 | 생산 상태·검사 여부·담당자 확인 여부를 별도로 이름 붙임 | ‘생산 종료/검사 완료/확인 필요’ 사례 해석 여부 |
| P5 | 인수인계 문장 작성·근거 확인이 반복 | 기록을 읽고 재정리해야 함 | AI가 사실·미확인 사항·확인 질문으로 요약, 원기록 링크와 사람 검토 | 초안 검토 시간·수정량·근거 없는 문장 수 |

P1·P4는 기본 화면 설계로 해결하고 P2를 작은 추가 기능으로 다룬다. P3는 입력 안내로 처리한다. P5는 수업 AI 요구와 연결한다. 문제마다 별도 화면·서비스를 만들지 않는다.

## 5. 가장 작은 추가 기능 제안

LOT 상세에 **‘품질 확인 메모’ 한 영역**을 추가한다.

1. 검사 결과에 규격 밖 측정값이 있으면 목록에서 ‘확인 필요’로 찾을 수 있다.
2. 품질 담당자가 ‘내가 확인’으로 담당을 맡는다. 담당자와 맡은 시각을 표시한다.
3. 관찰 사실·확인한 내용·남은 질문을 적고 ‘검토 기록’으로 남긴다.
4. AI 초안은 필요할 때 생성하고, 확정된 검토 기록과 구분한다.

상태 표현 제안: 담당 미지정 / 확인 중 / 검토 기록됨. **‘검토 기록됨’은 문제 해결·품질 합격·출하 승인과 다르다.** 부적합 결과를 수정하거나 숨기지 않는다. 재작업·재검사·종결 승인까지 포함하는 불량관리 시스템은 만들지 않는다.

동시 담당 지정은 한 명만 성공하고 다른 사람은 최신 담당자를 보도록 설계한다. MVP에서는 담당자 변경 UI는 제외하고 교대자는 원기록·현재 담당·검토 기록을 조회한다. 인계받은 사람이 다시 맡거나 추가 검토를 남기는 기능이 꼭 필요하면 사용자 백엔드 설계에서 먼저 정책을 확정한다. 변경·검토 이력이 있으면 기존 기록을 덮어쓰지 않는다.

이 제안은 아직 최종 DB/API 결정이 아니다. 별도 이슈 티켓·알림·댓글 플랫폼 대신 LOT과 연결된 담당·확인 기록으로 충분한지 사용자가 설계한다.

## 6. AI와 일반 로직의 구분

일반 로직: 규격 비교, 부적합수량·비율, 확인 필요 목록, 담당 지정, 상태 표시. AI 없이도 정상 동작해야 한다.

AI: 여러 기록과 자유문장 메모를 간결하게 정리하는 보조. 입력이 숫자 한 줄뿐이면 정형 문장으로도 충분하다. 이 경우 AI가 필요한 이유를 과장하지 않는다. 같은 LOT의 생산 메모·검사 메모·확인 기록을 제공할 때 요약의 효용을 검토한다.

출력 형식: 관찰 사실 / 아직 모르는 것 / 다음 확인 질문. 원인 가설을 사실로 쓰지 않으며 ‘설비 이상’ 등의 내용을 근거 없이 추가하면 실패 사례로 기록한다. AI는 담당 지정이나 확인 상태를 변경하지 않는다.

## 7. 발표용 전후 시나리오

가상 사례: BR-A LOT-A 5개 중 2개가 규격 밖이다. 작업 메모에는 ‘생산 중 특이사항 기록 없음’, 검사 메모에는 ‘대상 4·5 규격 이탈 확인, 원인 미확인’이라고 적혀 있다.

- 기존 상황 가정: 새 담당자가 검사표와 생산기록을 찾아보고, 이전 담당자에게 맡은 사람이 있는지 묻고 인수인계 내용을 다시 작성한다.
- 서비스 사용: ‘확인 필요’ 목록→LOT-A 상세→측정값·규격·메모 확인→담당 지정→요약 초안 검토→확인 메모 저장.
- 보여줄 변화: 사실을 찾는 경로와 담당 여부가 명확하고, 미확인 사항이 누락되지 않는다.
- 주장하지 않을 변화: 불량률 감소, 실제 원인 발견, 공정 안정성 확보, 산업 인증 준수.

동일 가상 데이터를 분리된 기록과 통합 화면으로 제공해 시간을 비교할 수 있다. 소수 참여자의 두 번째 시도는 익숙해진 효과가 있으므로 탐색적 사용성 확인으로만 보고한다. 측정 전 개선 수치를 만들어 넣지 않는다.

## 8. 지금 필요한 사용자 판단

우선 선택할 핵심 문제는 **‘부적합을 발견한 뒤 누가 어디까지 확인했는지 연결되지 않는 문제’**로 제안한다. 백엔드 전체 표를 채우기 전에 다음만 문장으로 정한다.

- 품질 담당자가 LOT을 열었을 때 가장 먼저 답을 얻어야 하는 질문은 무엇인가?
- 확인 담당자를 지정하는 작은 기능을 이번 범위에 넣을 것인가?
- ‘검토 기록됨’이 의미하는 업무 행위는 무엇인가? 단순 열람과 어떻게 다른가?

실제 경험·현장 사례가 있으면 가설을 수정한다. 없으면 가상 업체 사례로 명시하고 진행한다. 추가 현장 인터뷰가 구현의 필수 선행조건은 아니다.

기획 이후: 사용자가 선택한 문제·규칙을 바탕으로 백엔드 관계/API를 설계하고, 어시스턴트가 화면·코드·연결·검증을 수행한다. 이번 문서 작성으로 코드 구현이 완료된 것은 아니다.

## 현실성 보완: 기록량과 시스템 성숙도

2026-09-08 공식 자료 확인. [SAP 결함 기록 교육](https://learning.sap.com/courses/performing-quality-management-in-production/executing-defects-recording-using-the-inspection-lot-for-the-production-order_cec85d51-19e4-4f22-bd36-8fa89a3414c5)은 코드와 자유문장, 위치, 알려진 원인, 후속 조치를 구분한다. 경미한 결함은 분석에 필요한 기록만 남기고 포괄적 후속 처리를 하지 않아도 되는 경우가 있음을 설명한다. 이는 특정 SAP 업무 모델의 설명이며 모든 업체의 의무 기록 수준이나 평균 건수를 뜻하지 않는다.

따라서 ‘부서별 메모가 항상 많고 복잡하다’고 주장하지 않는다. 정상 반복 생산의 정형 데이터와 이상 대응의 여러 기록을 구분한다. 상용 MES/QMS는 이미 결함·담당·조치 기능을 제공하므로 기능 자체가 시장에 없다고 주장하지 않는다. 목표 가설은 기존 기능을 쓰기 어렵거나 기록이 연결되지 않은 특정 현장에서, 이상 1건의 사실·담당·확인 내용을 쉽게 모아볼 필요가 있다는 것이다. 메모가 짧은 데모라면 AI 요약 필요성도 별도 검증해야 한다.
