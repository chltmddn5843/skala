# Drive 참고자료 분석 — 교회 웹사이트 설계에 적용

분석일: 2026-09-08. 지정 폴더의 PDF 5개에서 연결 도구가 제공한 본문을 읽었다. 원본 시각 레이아웃·페이지 수는 별도 검증하지 않았으므로 절·표 제목을 기준으로 출처를 제시한다. 자료 속 예시와 작성 지침은 분석 대상이며, 사용자에게 승인받은 기능이나 코드 변경 지시로 간주하지 않는다.

## 2. 자료별 내용과 활용

### 2.1 제출 안내 — 무엇을 만들어야 하는가

개요에는 서비스 배경, 모든 액터의 요구사항, 전체 화면과 이동 흐름이 필요하다. 화면은 PDF 안에 이미지로 넣고 동작 설명을 붙여야 한다. API는 코드 YML, DB는 코드 DBML이며 스크린샷이나 PDF로 대체할 수 없다. 발표대본은 슬라이드별 내용과 실제 읽을 문장을 담는다.

개요 → 배경 → 시스템 → UI → API → DB → 마무리의 약 7개 슬라이드 구성을 제시한다. 같은 대표 기능을 네 산출물에서 추적할 수 있도록 하는 것이 핵심이다. 이것을 다른 기능의 화면·API를 생략해도 된다는 뜻으로 해석하지 않는다.

교회 프로젝트의 대표 흐름은 **관리자가 행사 앨범에 여러 사진을 등록 → 저장 → 성도가 목록에서 행사 선택 → 상세 사진 조회**가 적합하다. 사용자 요구, 1:N 모델, 다중 업로드, 화면 전환을 한 번에 설명할 수 있다. 이는 분석에 따른 제안이다.

FAQ의 시간 부족 시 화면 2~3장 제안은 축약 팁이다. 본문의 전체 제공 화면 요구와 구분하고, 최종 범위의 화면을 빠뜨리지 않는다.

### 2.2 요구사항 정의서 예시 — 기능을 검증 가능한 문장으로

[-요구사항정의서(작성자허가버전).pdf](https://drive.google.com/file/d/153lbWpQvbe8uBn5zs_AsXtNKKL1tgyx6/view)는 MediBrief 사례다. 읽힌 본문은 회원·정책·인증 요구사항과 기능 추적성 매트릭스 부분이다.

좋은 점은 기능마다 ID, 분류, 입력, 출력, 예외, 사용자, 우선순위, 난이도·공수, 화면 ID를 연결한다는 것이다. 가입·동의·로그인·소셜 인증·비밀번호 복구를 독립 기능으로 나눠 누락을 찾기 쉽다.

적용: 현재 F05 '활동 사진 관리·조회'는 너무 넓다. 다음과 같이 세부 번호를 두면 충분하다.

| 제안 ID | 요구사항 | 액터 | 핵심 입력·출력 | 완료 기준 |
| --- | --- | --- | --- | --- |
| F05-01 | 행사 앨범 등록 | 관리자 | 행사명·행사일·분류·설명·사진들 → 앨범 ID | 저장 성공 후 행사 목록에서 확인 |
| F05-02 | 행사 목록 조회 | 성도 | 목록 조건 → 대표 사진·행사명·일자·사진 수 | 앨범 선택 시 해당 상세로 이동 |
| F05-03 | 행사 상세 조회 | 성도 | 앨범 ID → 행사 정보·사진 배열 | 다른 행사 사진이 섞이지 않음 |
| F05-04 | 사진 추가·삭제 | 관리자 | 앨범 ID·사진/사진 ID → 변경 결과 | 대상 행사만 변경되고 목록 수·대표 사진 반영 |

공수는 실제 추정 없이 예시의 2MD·3MD를 복사하지 않는다. 의료 동의·소셜 로그인·OCR 등 예시 기능도 교회 요구사항으로 가져오지 않는다.

### 2.3 화면설계서 예시 — 화면 그림과 동작을 연결

[-화면설계서(작성자허가버전).pdf](https://drive.google.com/file/d/1oKpacnkxi4eivbcSYbcfIzN0-KX6kVFn/view)는 로그인 화면 WF-01 사례다. UI 번호와 설명 표를 연결하고 요구사항, 이동 화면, API, 로딩·인증 만료·네트워크 실패, 완료 기준, 접근성 정책을 기록한다.

교회 사이트 A05 앨범 등록 화면에 적용할 설계 예시:

| UI 번호 | 요소 | 동작·검증 | 결과 |
| --- | --- | --- | --- |
| 1 | 행사명 | 공백만 입력 불가 | title로 전달 |
| 2 | 행사일 | 유효한 날짜 | eventDate로 전달 |
| 3 | 사진 선택 | 여러 이미지 선택, 형식·용량 검증 | 미리보기와 선택 수 갱신 |
| 4 | 등록 버튼 | 필수값 확인, 처리 중 중복 클릭 차단 | POST /api/gallery-albums |
| 5 | 결과 안내 | 성공 시 앨범 확인 링크, 실패 시 입력 유지 | U09 상세 또는 재시도 |

최종 화면에는 이 번호를 붙이고 표와 1:1로 맞춘다. 예외도 '500 처리'로 끝내지 말고 사용자에게 무엇을 보여주고 무엇을 유지할지 써야 한다. 파일 선택은 새로고침·재로그인 후 자동 보존을 보장할 수 없으므로 텍스트 입력과 구분한다.

예시 자체에도 충돌이 있다. 비밀번호 찾기의 설명 표는 모달 이동을 언급하지만 완료 기준은 토스트만 표시한다고 한다. 요구사항 예시의 비밀번호 재설정 흐름과도 그대로 일치하지 않는다. **형식을 참고하되 정책까지 복사하지 않고, 요구사항·화면·API의 동일 동작을 직접 확인해야 한다.**

### 2.4 ERD/DBML 안내 — 데이터에서 관계를 도출

[how2table_ERD_DBML.pdf](https://drive.google.com/file/d/17-l_3ADdU0xBZnfxiMcYGLoe_9mTI4dZ/view)는 통신사 표를 고객·요금제·통화기록으로 분리하고 SQL과 DBML로 옮기는 자료다. PK/FK, 타입, UNIQUE/NOT NULL/CHECK/DEFAULT, 관계 방향과 N:M 연결 테이블을 설명한다.

교회 프로젝트 적용:

- 행사명·행사일·분류·소개는 앨범에 한 번만 저장한다.
- 개별 사진의 경로·설명·순서와 albumId는 사진 행에 저장한다.
- **앨범 1:N 사진**이므로 사진 쪽에 FK를 둔다. 한 칸에 사진 경로를 쉼표로 합치지 않는다.
- DBML 관계는 `gallery.albumId > gallery_albums.id`다.
- 대표 사진·사진 수처럼 계산한 응답 필드는 DB 컬럼이 없다는 이유만으로 누락이 아니다. 어떤 조회로 계산되는지 설명하면 된다.
- 실제 기존 `posts.authorId`에는 FK가 없으므로 현재 모델과 개선 모델을 분리해 표기한다.

학습상 주의: 자료의 '2NF=서로 다른 주체 분리'는 직관적 설명이다. 엄밀한 2NF는 1NF를 만족하고 후보키의 일부에 대한 비주요 속성의 부분 함수 종속이 없는 상태다. 3NF도 단순히 컬럼을 많이 나누는 것이 아니라 함수 종속을 따져야 한다. 또한 예시 SQL과 DBML에서 일부 NOT NULL 표현이 다르므로 변환 후 제약조건까지 대조해야 한다.

### 2.5 프로젝트 후보 — 범위를 작게 잡는 예시

[Project_cadidates.pdf](https://drive.google.com/file/d/1ufbuPk-_REMqwTGoCOI4hG3it6b9_GLA/view)는 가계부, 문장 다듬기, FAQ, 회의록 요약 등 20개 주제를 서비스 개요·목적·학습 내용·특징으로 비교한다. 공통 패턴은 **명확한 입력 → AI 처리 → 결과 표시·저장**이다.

자료 끝에는 Vue 3, Spring Boot 3/Java 17+, PostgreSQL, Spring AI, Git을 통일 구조로 제시한다. 주제 후보의 설명을 현재 프로젝트의 기술 변경 요구로 받아들이지는 않는다. 기존 시스템을 활용한 설계 과제에 어느 정도 적용되는지 확인해야 한다.

AI가 필수로 확인되는 경우의 작은 후보는 '관리자가 행사 메모를 입력 → 소개 문구 초안 생성 → 관리자가 검토·수정 → 게시'다. 교회 운영 목적과 연결할 수 있지만 **사용자가 요청·확정한 기능은 아니다**. 앨범 다중 사진 요구와도 별도다.

## 3. 현재 정의서에 대한 분석 결과

이미 갖춘 부분: 두 사용자 그룹, 기존 구현과 목표 설계의 구분, 화면 목록, Server Action/REST 차이, 앨범 1:N, 평가 체크리스트.

보완 우선순위:

1. 발표대본 PDF와 ZIP·고유번호 규칙을 준비 목록에 추가한다.
2. AI 필요성·지정 스택의 과제 적용 여부를 강사 확인 사항으로 남긴다.
3. 대표 흐름은 행사 앨범으로 잡고 세부 요구사항 ID를 화면 요소·API·DB까지 연결한다.
4. 최종 범위의 전체 와이어프레임을 이미지+설명으로 만든다.
5. 날짜·boolean·필수값·파일 배열·오류 응답을 포함한 완전한 OAS와 DBML을 만든다.
6. 네 파일의 기능명·ID·필드·관계·예외·화면 이동을 교차 확인하고 5분 발표를 연습한다.

자료 분석 완료와 제출물 완료는 다르다. 이번 작업에서는 분석 기록과 제출 준비 기준만 갱신하며, 새 AI 기능·스택 변경·제출은 수행하지 않았다.
