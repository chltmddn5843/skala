## 실습·과제 체크리스트

체크되지 않은 항목은 아직 완료를 확인하지 못했다는 뜻이다.

### 1일차 — 서비스 기획

- [X] 서비스 이름, 대상 사용자, 해결할 문제와 배경을 정의한다.
- [X] 문제를 해결하는 핵심 기능과 액터별 권한·행동을 정리한다.
- [X] 제공할 전체 화면의 와이어프레임과 이동 흐름을 만든다.
- [X] 화면별 버튼, 입력값, 표시 데이터, 동작을 설명한다.

### 2일차 — 시스템 설계

- [ ] 화면과 기능에 필요한 엔터티, 속성, PK/FK, 관계, 타입·제약조건을 DBML로 작성한다.
- [ ] 화면에서 호출할 API 전체를 OAS YAML로 작성한다.
- [ ] Method, 경로, Path/Query/Body 입력, 응답, 오류 코드와 공통 스키마를 정의한다.
- [ ] 요구사항 → 화면 → API → 데이터 필드를 대조해 누락·불일치를 확인한다.

### 3일차 — 보완·제출·발표

- [ ] 오전: 기획과 설계를 보완하고 산출물 간 일관성을 최종 확인한다.
- [ ] 13:00~14:00: 아래 세 파일을 정리해 제출한다. 제출 완료 여부는 별도 확인한다.
- [ ] 14:30~17:00: 반별 개인 발표, 1인 5분.

## 핵심 이론 — 설계하면서 확인할 내용

| 개념                  | 알아야 할 핵심                                                                                           | 내 프로젝트에서 확인할 질문                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 액터·요구사항        | 액터는 시스템과 상호작용하는 역할이며 기능은 해결할 문제에 연결된다                                      | 누가 어떤 목적으로 이 기능을 사용하는가?                              |
| UI 흐름·와이어프레임 | 화면 구성뿐 아니라 입력·행동·화면 이동을 명시한다                                                      | 버튼을 누르면 무엇을 보내고 어떤 결과를 보여주는가?                   |
| 데이터 모델           | 엔터티와 속성, PK/FK, 1:N·M:N 관계로 필요한 데이터를 표현한다                                           | 화면에 보여줄 값은 어디에서 오며 어떻게 연결되는가?                   |
| REST API              | 리소스와 HTTP 메서드로 인터페이스를 정의한다                                                             | 조회·생성·변경·삭제에 맞는 요청인가?                               |
| OAS                   | YAML/JSON으로 API 계약을 기술한다.`paths`에 작업, `components.schemas`에 공통 데이터 구조를 정의한다 | 요청과 응답만 보고 화면과 서버를 각각 설계할 수 있는가?               |
| 설계 일관성           | 요구사항·UI·API·DB가 같은 기능과 데이터를 설명해야 한다                                               | 화면 필드가 응답에서 빠지거나 저장할 데이터가 DB에서 빠지지 않았는가? |

근거: 교재 1~6쪽, 8~12쪽. 마지막 열은 학습용 확인 질문이다.

## 시험 대신 발표 준비

공지에 따라 이번 과정은 퀴즈 없이 개인 발표로 마무리한다. 아래 시간 배분은 어시스턴트 제안이다.

- 0:00~0:40: 대상 사용자와 문제, 서비스 목적.
- 0:40~2:30: 핵심 사용자 시나리오를 화면 흐름으로 설명.
- 2:30~4:20: 해당 흐름에 연결되는 API·데이터 관계 및 설계 판단.
- 4:20~5:00: 고려사항과 마무리.

연습 질문: 이 기능이 필요한 이유는 무엇인가? 화면 하나의 입력부터 API·DB까지 설명할 수 있는가? 관계를 1:N 또는 M:N으로 정한 이유는 무엇인가? 실패 시 어떤 응답을 정의했는가?

## 다음 단계와 미확인 사항

1. 사용자가 생각한 서비스 주제와 현재 진행 내용을 확인한다.
2. 확인된 주제를 기준으로 서비스 개요·액터별 기능부터 작성한다.
3. 실제 3일차 날짜와 제출 경로는 공지에 없어 확인이 필요하다. 임의로 날짜를 계산하지 않는다.

교재 제목에 AI가 있지만 확인한 평가 기준에는 특정 AI 모델·기능을 필수로 명시하지 않는다. 강사의 추가 요구가 있다면 반영한다.
