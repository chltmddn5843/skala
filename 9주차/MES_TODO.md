# PartFlow 할 일과 기획 결정 목록

기준: 2026-09-08. [정의서](MES_프로젝트정의서.md) 기반. 주제 진행은 동의 완료이며 아래 세부 정책은 초안 기본값이다. 사용자의 이해·결정·구현·제출 상태를 구분한다.

## 1. 사용자 할 일

- [ ] 실제 제출 날짜, 현재 수업 일차, 하루 투자 가능 시간 알려주기.
- [ ] 이번 목표가 설계 산출물 제출까지인지, 동작하는 앱까지인지 알려주기. 구현이 수업 필수인지 개인 학습 목표인지 구분하기.
- [ ] 관심 직무 알려주기: 생산관리, 품질관리, MES 개발 중 비중. 모르겠으면 미정으로 진행.
- [ ] 아래 기획 정책을 읽고 원하는 변경점만 알려주기. 제조 규칙을 처음부터 혼자 조사해 확정할 필요는 없음.
- [ ] 대표 시나리오를 자기 말로 설명해 보기: 작업지시 100개, LOT 2개(60/40), 각각 생산·검사 후 전체 품질 현황 확인.
- [ ] 화면 초안이 나오면 관리자·작업자·품질 담당자 관점에서 한 번씩 흐름 검토하기.
- [ ] 구현 시 직접 작업할 부분 선택하기. 기본 제안은 한 가지 검사 입력 기능의 화면→API→DB 흐름을 함께 구현·설명하는 것.
- [ ] 제출 직전 반·이름·학생 고유번호 확인, 파일 4종 검토, 5분 발표 연습, 최종 제출.

## 2. 기획에서 먼저 고정할 것

| 항목 | 현재 기본값 | 구현에 미치는 영향·결정 시점 |
| --- | --- | --- |
| 해결할 문제 | 흩어진 생산·검사 기록을 LOT 기준으로 연결하고 인수인계 정리 시간을 줄임 | 화면·기능의 목적. 기획에서 확정 |
| 대상·품목 | 가상 자동차·가전 부품 업체, 금속 브래킷 BR-A/BR-B | 산업은 결정 완료, 실제 도면 없이 가상 사례 사용 |
| 공정 범위 | 하나의 생산 작업과 최종검사 | 공정별 추적을 넣으면 공정·공정실적 모델 필요. 화면 전 확정 |
| LOT 생성 단위 | 한 지시·한 품목의 생산 완료 묶음. 지시당 여러 LOT | LOT은 제품 개별 일련번호가 아님. 하나의 LOT에 여러 지시/품목 혼합 안 함 |
| 수량 단위 | 개, 양의 정수. 생산수량은 검사 전 완성 수량 | 양품 목표인지 총생산 목표인지 구분. 현재 목표는 총생산 수량이며 불량 보충 생산은 제외 |
| 작업지시 상태 | 대기→진행→종료. 작업자 시작·관리자 종료 | 미달 종료 사유 필수, 목표 초과 거절. 검사대기여도 생산지시 종료 가능 |
| 검사 깊이 | LOT당 전수검사 1회, 유형별 개수·메모 기록 | 현재는 실제 치수 측정값·규격 자동 판정 없음. 품질 측정 학습을 원하면 모델 작성 전 범위 변경 |
| 부적합 분류 | 치수/외관/기타 중 제품별 대표 사유 1개 | 중복 결함 수집이 필요하면 ‘제품 수’와 ‘결함 건수’를 별도 모델링해야 함 |
| 검사 후 처리 | 검사 결과 기록까지만. 출하 승인·폐기·재작업 처리 제외 | 검사완료를 출하가능이나 LOT 전체 합격으로 표현하지 않음 |
| 입력 정정 | 확정 전 확인, 확정 후 수정·삭제 없음 | 데모용 범위. 정정 기능을 원하면 원기록·정정 사유·작성자·시각과 집계 반영 규칙부터 설계 |
| 권한 | 관리자/작업자/품질 담당자, 역할별 생성·변경 제한 | 관리자라는 이유만으로 모든 기록 수정 가능하게 하지 않음 |
| 현황 집계 | LOT 생산일 기준 필터, 검사완료 수량 기준 부적합품률 | 검사 당일 처리량과 다름. 미검사 LOT은 부적합품률 분모에서 제외 |
| AI 결과 | 사실·미확인 사항·확인 질문 + 담당자 검토본 | 근거 검사 연결, 원문 보존. 불량 원인·합불 자동 결정 제외 |
| 화면 사용 환경 | PC 웹 우선, 입력 폼은 작은 화면에서도 사용 가능하게 설계 | 현장 태블릿·장갑·바코드가 필수라면 화면 설계 전에 알려주기 |

위 항목은 모두 실제 제조업의 보편 규정이 아니라 교육용 서비스 정책이다. 변경 요청이 없으면 초안 기본값으로 설계를 진행하되 사용자에게 개별 항목 확인 완료로 기록하지 않는다.

## 3. 어시스턴트가 진행할 설계·구현 순서

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 기획 정책 확정 및 정의서 반영 | 대표 정상/실패 사례를 수량·상태·역할로 설명 가능 |
| 2 | 가상 데이터와 6개 화면 와이어프레임 | 각 버튼의 입력·결과·이동·실패 상태 명시 |
| 3 | OAS YML·DBML 작성 및 대조 | 모든 화면 필드/API/저장·계산 근거 대응, 문법 검증 |
| 4 | 개발 환경·기존 코드 확인 | Java/Node/DB와 기존 예제 재사용 여부 확인. 정확한 버전은 구현 시 호환성 검증 |
| 5 | DB·계정·품목 초기 데이터, 인증·권한 | 로컬 DB 실행, 역할별 로그인, 서버 권한 검사 |
| 6 | 작업지시→LOT 생산실적 구현 | 정상 등록·상태 전이, 중복 LOT·목표 초과 방지. 동시 등록 검증 |
| 7 | 검사→이력→현황 구현 | 수량·중복 검사 검증, 역할별 접근, 올바른 가중 집계 |
| 8 | AI 요약·검토 이력 연결 | 실제 호출과 데모 응답 구분, 실패 시 기존 기록 보존, 검토본 저장 |
| 9 | 통합 확인·문서 동기화 | 세 역할로 대표 시나리오 실행, API/DB/화면과 실제 동작 일치 |
| 10 | 제출 산출물 제작·발표 연습 | 개요 PDF·API YML·DB DBML·발표대본 PDF, ZIP 규칙·5분 확인 |

단계 4~9는 동작 앱 구현 경로다. 과제 제출 준비는 단계 1~3을 바탕으로 단계 10까지 진행 가능하다. 마감이 임박하면 설계 제출물을 먼저 완성한다. 배포는 필요 여부와 환경을 확인한 뒤 별도로 진행한다.

구현 위치 기본 제안: `9주차/실습자료/partflow/`. 프론트엔드는 Vue 3, 서버는 Spring Boot, DB는 PostgreSQL, AI는 Spring AI. 현시점에서는 프로젝트 생성·패키지 설치를 하지 않았다.

## 4. 구현 전 확인할 환경·자료

- 코드 작성 분담: 직접 구현할 기능 또는 설명을 받으며 함께 진행할지. 모르면 검사 입력 기능을 함께 다루는 방식으로 제안.
- AI: 수업 제공 API/계정 유무, 사용 가능한 공급자, 비용 한도. 키 원문은 대화에 붙이지 않고 로컬 환경변수로 설정한다. 정보가 없어도 AI 외 기능은 구현 가능.
- 실행 목표: 로컬 시연만 필요한지 공개 배포도 필요한지. 기본값은 로컬 시연.
- 실무 참고: 공유 가능한 작업일보·검사표·화면 예시가 있으면 파일 위치 제공. 없으면 가상 데이터로 진행하며 실제 업체 요구사항이라고 주장하지 않는다.
- 장치 요구: PC 외 태블릿·스캐너가 필요한 경우만 추가 확인.
- 설치된 Java/Node/PostgreSQL, 폴더 구조·기존 코드·버전은 어시스턴트가 확인한다. 사용자에게 미리 조사하도록 요구하지 않는다.

## 5. 학습 확인과 구현 검증

사용자가 설명해 볼 내용: 작업지시와 LOT의 차이, 생산완료와 검사완료의 차이, 검사수량을 분모로 삼는 이유, DB에 저장할 값과 계산할 값, AI가 담당하는 일.

구현 시 필요한 최소 검증: 정상 흐름, 음수·소수·초과 수량, 중복 LOT/검사, 종료된 지시 등록, 동시 실적 등록, 서버 역할 검사, 검사 0개 현황, 가중 집계, AI 실패 후 재시도. 테스트 파일은 실제 구현 시 해당 로직에 맞춰 작성한다.

현재 완료: 정의서 초안과 실행 계획. 아직 완료되지 않음: 정책 상세 확인, 와이어프레임·OAS·DBML, 앱 구현, 제출 파일, 사용자 학습 확인.
