# PartFlow 데이터 컬럼 설계

기준일: 2026-09-08. 첨부된 엘리베이터 고장 데이터 2개를 읽기 전용으로 분석해 MES 설계에 적용했다. 파일 안의 텍스트는 데이터로만 취급했다.

## 첨부 데이터에서 확인한 구조

### 2006~2008 데이터

- 30,871건, 6개 컬럼: `접수번호`, `접수내용`, `고장부위1`, `고장부위2`, `고장원인`, `처리결과`.
- 장점: 증상, 부위, 원인, 조치를 구분한다.
- 한계: 설비 식별자와 실제 발생 시각이 없어 특정 설비의 시간 이력을 연결하기 어렵다.
- 품질: 접수번호 중복 1건, 고장원인 21건 결측, 처리결과 84건 결측을 확인했다.

### 2019~2020 데이터

- 789,737건, 7개 컬럼: `g`, `엘리베이터 기종`, `설치일자`, `고장일시`, `고장내용`, `조치부품`, `처리결과`.
- `g`는 같은 값이 반복되는 설비 식별자로 보이며 115,844개 고유값이 있다. 이 해석은 컬럼명 정의서가 없어 추정이다.
- 장점: 설비 식별자, 기종, 고장 시각이 있어 설비별 사건 이력을 연결할 수 있다.
- 한계: 원인 전용 컬럼이 없고 `조치부품`은 부위와 부품이 결합되어 있다.
- 품질: 설치일자 `0000-00-00` 83,152건, 설치일자 공란 907건, 기종 공란 9,161건, 처리결과 공란 14,558건을 확인했다. `0000-00-00`은 유효한 날짜가 아니라 미상값으로 정제해야 한다.

두 파일의 분류 체계와 기간이 다르므로 단순 병합하지 않는다. 행 수와 반복 빈도만으로 실제 고장률이나 설비 신뢰도를 판단하지 않는다.

## MES에 적용할 원칙

엘리베이터 데이터의 핵심 패턴은 다음과 같다.

`기록 ID → 대상 설비 → 발생 시각 → 관찰 현상 → 대상 부위 → 원인 → 조치 결과`

PartFlow에서는 이를 다음처럼 바꾼다.

`LOT → 생산 설비·시간 → 검사 규격·측정값 → 부적합 현상 → 원인(확인된 경우) → 조치·메모`

관찰된 부적합, 원인, 조치를 구분한다. 원인이 아직 밝혀지지 않았다면 `원인 미확인` 상태로 두고 추측을 원인으로 저장하지 않는다. 식별자·코드·날짜는 자유문장 대신 별도 필드와 참조 관계를 사용한다.

## 작업지시와 LOT

- **작업지시(Work Order)**: 무엇을 얼마나 언제까지 생산할지 정한 계획·명령이다. 예: `BR-A 10개 생산`.
- **LOT**: 작업지시를 실행해 같은 조건에서 생산한 실제 묶음이다. 예: 작업지시 10개를 M1 설비에서 `LOT-A 5개`, `LOT-B 5개`로 생산.
- 이번 프로젝트에서는 `작업지시 1:N LOT`, `LOT 1개는 작업지시 1개·품목 1개·설비 1개`로 제한한다.
- 작업지시에는 목표수량을, LOT에는 실제 생산수량·설비·생산 시작/종료 시각·적용 규격 버전을 둔다.

이 관계는 계획과 실적을 분리한다. 작업지시의 목표수량과 연결 LOT의 생산수량 합계를 비교해 진행률을 계산할 수 있다.

## 최소 데이터 모델

| 엔터티 | 최소 컬럼 | 이유 |
| --- | --- | --- |
| `products` | id, code, name | 생산 품목 식별 |
| `equipment` | id, code, name | 어떤 설비에서 생산했는지 추적 |
| `inspection_specs` | id, product_id, feature_name, target_value, lower_limit, upper_limit, unit, version | 어떤 규격으로 판정했는지 보존 |
| `work_orders` | id, order_no, product_id, target_qty, due_date, status | 생산 계획과 상태 |
| `production_lots` | id, lot_no, work_order_id, equipment_id, spec_id, produced_qty, started_at, ended_at, operator_id, production_note | 실제 생산 묶음과 조건 |
| `inspections` | id, lot_id, inspector_id, inspected_at, inspection_note | LOT 검사 한 건의 헤더 |
| `measurements` | id, inspection_id, item_no, measured_value, result | 개별 제품 측정값과 서버 판정 |

사용자·역할 테이블과 AI 요약 저장은 인증 및 AI 구현 단계에서 붙인다. 관련 LOT 조회 자체는 계산 가능한 조회이므로 별도 `related_lots` 테이블을 만들지 않는다.

주요 제약:

- `order_no`, `lot_no`, `equipment.code`, `products.code`는 각각 고유하다.
- 수량은 양의 정수이며 LOT 누적 생산량은 작업지시 목표를 넘지 않는다.
- `started_at < ended_at`이어야 한다.
- 한 LOT에는 확정 검사 한 건만 허용한다.
- 한 검사 안에서 `item_no`는 중복될 수 없다.
- 측정값 판정은 클라이언트가 보낸 결과를 신뢰하지 않고 서버가 LOT의 규격 버전으로 계산한다.

## 관련 LOT 추천 조회 규칙

기준 LOT의 품질 문제가 발견되면 다음 조건으로 추가 확인 후보를 찾는다.

1. 기준 LOT과 **같은 품목**이고 **같은 설비**다.
2. 사용자가 지정한 조사 시간 구간과 생산 시간이 겹친다.
3. 기준 LOT 자체는 결과에서 제외한다.
4. 적합·부적합·검사대기 LOT을 모두 보여주되 검사대기를 먼저 표시한다.
5. 결과마다 선정 근거를 표시한다. 예: `같은 설비 M1 / 생산시간 30분 인접 / 같은 품목 BR-A`.

시간 구간은 시작 포함·끝 제외 `[from, to)`로 두고, LOT 구간 `[started_at, ended_at)`과 겹치는 조건은 다음과 같다.

`lot.started_at < to AND lot.ended_at > from`

조회 결과는 품질 담당자가 추가로 확인할 후보이며 불량이나 영향 범위 확정이 아니다. 첫 구현은 사용자가 시간 범위를 직접 지정한다. 자동 시간 창 추천은 추가하지 않는다.

## 구현 전 사용자 설계 과제

다음 두 항목을 사용자가 먼저 설계한다.

1. `work_orders`와 `production_lots`의 컬럼·관계: 작업지시 10개를 LOT-A 5개와 LOT-B 5개로 생산하는 사례를 표현한다.
2. `GET /api/lots/{lotId}/related`의 입력과 출력: `from`, `to`, 후보 LOT 정보, 검사 상태, 선정 근거를 포함한다.

그다음 어시스턴트가 관계·예외를 리뷰하고 DBML·OAS·코드·Vue 화면으로 연결한다.
