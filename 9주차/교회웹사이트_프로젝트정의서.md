# 교회 웹사이트 — 웹 서비스 프로젝트 정의서

상태: 기획 초안, 2026-09-08. 사용자 설명으로 확인된 사실과 확인할 내용을 구분한다.
기준: 교재 4쪽 정의서 목차, 5~6쪽 평가 기준. 쪽수는 슬라이드 하단 번호.

현재 확인된 사실: 사용자가 개발 중인 교회 웹사이트가 있고 Cloudflare에 배포되어 있다. GitHub의 `chruch` 작업 내용이 있으며 추가 기능과 방향은 아직 문서화되지 않았다. 저장소 검색에서 대상을 찾지 못해 소스·실제 화면·DB·API는 미검토 상태다.

## 1. 서비스 개요

- 서비스 이름: 미정. 작업명은 교회 웹사이트.
- 목적·배경: 교회 웹사이트의 기존 기능과 향후 기능을 정리하고, 실제 이용자의 문제에 연결되는 서비스로 설계한다. 구체적인 이용자 문제와 운영 배경은 사용자 확인 필요.
- 핵심 가치: 일반 성도가 교회 정보와 소식을 확인하고, 관리자가 정보를 직접 게시할 수 있도록 한다(사용자 설명 기반).
- 주요 기능: 교회 정보·소식 조회, 관리자의 예배 링크·공지사항·활동 사진·동향 소개 업로드. 구현 여부는 코드 확인 전까지 미확인.
- 이번 과제의 범위: 서비스 기획 및 기능 정의, UI 흐름, 시스템 설계 및 데이터 모델링.
- 현재 운영 환경: Cloudflare 배포는 사용자 확인 사항. Pages/Workers 여부, 데이터 저장소 및 배포 URL은 미확인.

기능은 `현재 구현 확인`, `사용자 계획`, `설계 제안`, `이번 제출 범위 제외`로 구분한다. 기존 코드에 있다는 이유만으로 모든 기능을 이번 과제 범위에 포함하지 않는다. 창의성보다 기능의 명확성과 실현 가능한 범위를 우선한다.

## 2. 시스템 액터 정의

사용자가 두 액터를 확인했다. 성도의 회원가입·로그인 필요 여부, 관리자 계정 발급 방식은 아직 미확정이다.

| 액터      | 목적                         | 사용자 확인 기능                                                  |
| --------- | ---------------------------- | ----------------------------------------------------------------- |
| 일반 성도 | 교회 정보를 얻고 소식을 확인 | 교회 정보·소식 조회                                              |
| 관리자    | 교회 정보를 사이트에 게시    | 예배 링크 등록, 공지사항 업로드, 활동 사진 업로드, 동향 소개 게시 |

| 기능 ID | 액터      | 요구사항                    | 설계 시 확인할 내용                           |
| ------- | --------- | --------------------------- | --------------------------------------------- |
| F01     | 일반 성도 | 교회 정보를 조회한다        | 소개 정보 항목과 기존 화면                    |
| F02     | 일반 성도 | 교회 소식을 조회한다        | 공지·사진·동향의 목록/상세 구성과 공개 범위 |
| F03     | 관리자    | 예배 링크를 등록한다        | 예배명·일시·URL 등 필드와 성도 측 노출 위치 |
| F04     | 관리자    | 공지사항을 업로드한다       | 제목·본문·첨부 등의 필요 여부               |
| F05     | 관리자    | 교회 활동 사진을 업로드한다 | 단일 사진/앨범, 설명, 공개 범위               |
| F06     | 관리자    | 교회 동향 소개를 게시한다   | 공지와 별도 유형인지, 필요한 콘텐츠 항목      |

F01~F06은 사용자 요구사항이며 구현 완료를 뜻하지 않는다. 수정·삭제·임시저장·예약 게시 등은 아직 확정하지 않았다. 일반 성도의 예배 링크 이용 방식도 화면 확인 및 사용자 의도에 맞춰 정한다.

액터마다 사용자 목적, 허용 기능, 접근 가능한 데이터, 제한 조건을 명시한다. 기능 요구사항은 아래 형태로 구체화한다.

> 기능 ID / 사용하는 액터 / 해결할 문제 / 입력 / 정상 결과 / 실패 조건 / 현재 상태 / 이번 제출 포함 여부

## 3. UI 흐름 (와이어프레임)

저장소의 라우트·화면·사용자 동작을 확인해 현재 화면 목록을 작성한 뒤, 추가 기능에 필요한 화면을 구분한다.

각 화면에는 화면 ID, 진입 경로, 표시 데이터, 입력 항목, 버튼 동작, 다음 화면, 빈 결과·입력 오류·접근 제한·서버 실패 시 동작을 기술한다. 해당 기능이 없는 화면에 불필요한 상태를 일괄 추가하지 않는다.

최종 기술서 PDF에는 **전체 제공 화면의 와이어프레임과 UI 흐름을 화면 캡처로 포함**한다. 화면 링크만 넣은 문서는 제출 요건을 충족하지 않는다. 현재 초안에는 화면 캡처가 없어 이 요건은 미완료다.

## 4. 데이터 모델 설계

기존 데이터 저장 방식과 스키마는 미확인이다. 정적 콘텐츠, API 응답, DB 저장 데이터, 외부 서비스 데이터를 구분한 뒤 실제 저장해야 할 데이터의 엔터티를 도출한다.

각 엔터티의 속성·타입·필수 여부·PK/FK·유일성 등 제약조건과 관계의 수를 명시한다. UI 표시값이 DB 속성과 직접 대응하지 않으면 계산값·외부 데이터 등 출처를 설명한다. M:N 관계가 필요하면 연결 엔터티를 정의한다.

최종 산출물: `{반_이름_프로젝트명}-DB.dbml`. 현재는 모델 미확정으로 미작성.

## 5. API 명세 정의

기존 API 호출과 서버 핸들러는 미확인이다. 각 화면 동작을 기준으로 실제 호출과 추가 설계를 나누고 정적 화면에는 불필요한 API를 만들지 않는다.

각 API는 Method·Path, Path/Query/Body 입력, 필수값·타입, 성공 응답, 오류 응답 및 공통 스키마를 명시한다. 화면 필드와 데이터 모델 사이의 변환도 설명한다. Security Schemes는 과제 평가에서 제외되지만 액터별 접근 권한과 필요한 오류 처리는 기능 설계에 남긴다.

최종 산출물: `{반_이름_프로젝트명}-API.yml` (OAS). 현재는 기능 미확정으로 미작성.

## 6. 고려사항

- 기존 구현은 코드 근거로, 운영 배포 상태는 배포 환경 확인 근거로 따로 판단한다.
- 추가 기능은 사용자가 해결하려는 문제와 우선순위를 받은 뒤 이번 제출 범위를 정한다.
- 실제 구현과 설계 목표가 다르면 차이를 명시한다. 이번 작업의 중심은 기획·설계 문서화다.
- 교인 등 개인 정보를 취급하는 기능이 포함되면 수집 필드, 조회·수정 주체와 공개 범위를 구체적으로 정한다.
- Cloudflare 배포 구조는 기존 구성 확인 후 필요한 수준으로 설명한다. 새 인프라 도입을 먼저 결정하지 않는다.

## 평가 기준에 따른 검토 방법

| 평가 항목           | 정의서에 남길 근거                                             | 현재 상태                   |
| ------------------- | -------------------------------------------------------------- | --------------------------- |
| 서비스 정의·명확성 | 대상 사용자 → 문제 → 기능의 연결, 범위와 제외 항목           | 사용자 방향 확인 필요       |
| UI 흐름·화면 설계  | 모든 요구 기능의 화면, 버튼·입력·표시 데이터, 화면 캡처      | 저장소·화면 확인 필요      |
| 데이터 모델         | 화면/API에 필요한 데이터의 출처, 엔터티·PK/FK·관계·제약조건 | 소스와 기능 확인 필요       |
| API 명세            | 화면 동작 전체의 API, 요청·응답·오류와 스키마                | 소스와 기능 확인 필요       |
| 산출물 일관성       | 아래 연결표로 누락과 이름·타입 불일치 검토                    | 기능 확정 후 작성           |
| 납기·발표          | 3일차 14시 제출, PDF/YML/DBML, 개인별 5분 발표                 | 실제 날짜·제출 경로 미확인 |

기능을 확정하면 `기능 ID → 액터 → 화면 ID·동작 → API → 데이터 엔터티·필드 → 예외 상황`을 한 행씩 연결한다. 이 연결표를 기준으로 화면에 없는 기능, 누락된 API, 저장할 수 없는 입력값을 확인한다.

## 사용자에게 확인할 내용

1. 대상 GitHub 저장소 URL과 `chruch`가 하위 폴더라면 그 경로. 별도 작업 브랜치가 있다면 브랜치명.
2. 두 액터와 업로드할 콘텐츠는 확인 완료. 기존 코드를 읽은 뒤 추가 기능과 기존 기능의 차이, 공개 범위와 우선순위를 확인한다.
3. 실제 화면 확인을 위한 배포 URL(저장소에서 확인되면 재질문하지 않음).

위 정보가 들어오면 기존 기능 조사 → 추가 기능 정리 → 제출 범위 결정 → 여섯 목차 상세화 순서로 진행한다.
