### 2. Self-Consistency

동일한 문제를 서로 다른 경로로 여러 번 풀게 한 뒤, 공통적으로 나온 답만 다수결로 나온 최종 답으로 설정함

**즉, 교차 검증을 하는 것임**

- 적합 케이스
  - 맞다, 틀리다가 명확히 갈리는 계약 리스크 경우
  - 이상 탐지
  - 법무, 재무, 운영 처럼 여러 관짐이 섞인 평가를 진행할 때
- 비적합 케이스
  - 자원 소모가 많은 만큼 다양성이 필요한 창작성 답변에는 부적합
  - 몇 번, 어떤 기준으로 교차검증할지 프롬프트에 명시할 것

**> 평가 : 1. 실제로 여러 경로,관점이 제시됐는가 2. 경로 간 불일치 시 처리 검증 규칙이 있는가(다수결) 3. 비용 대비 정확도 향상을 설명할 수 있는가?**

### 3. ReAct (Reason + Act)

추론과 도구 호출(검색, 조회)를 번갈아 수행하는 기법

1. 모델 생각 -> 2. 도구 호출 후 조회 -> 3. 결과 관찰 -> 4. 다시 생각 반복하여 **추론하기**

- 적합 케이스
  - 정책 문서 조회가 필요한 경우
  - 대량 거래 데이터에서 조건에 맞는 행을 필터링해야할 경우
  - 실시간 정보가 답의 정확도를 좌우하는 경우
- 비적합 케이스
  - 이미 아는 지식만으로 충분한 질문엔 불필요한 지연만 발생
  - 조회 결과를 검증 없이 믿으면 안됨
  - *무한 반복없도록 최대 횟수 정하기*

> ### ex
>
> Thought: 먼저거래처별평균금액을확인해야한다.
>
> Action: 거래처V009의최근10건평균금액을조회하라.
>
> Observation: 평균168,000원
>
> Thought: 이번건(6,720,000원)은 평균 대비 약 40배로 이례적이다. 이상거래로판단한다

**> 평가: 1. 실제 조회,도구 호출 단계가 프롬프트에 있는가. 2. 조회 결과를 다음에 추론에 반영하는 (생각)루트가 있는가. 3. 최대 반복 횟수 등 무한루프 방지 장치가 있는가**

### 추가 )하네스 엔지니어링

단일 거대 프롬프트 대신 파이프라인으로 작업을 구조화하는 기법

- 하나에 프롬프트에 모든 지시가 아닌, 역할별로 단계를 나눠서 입력과 출력을 세분화 한 것임
- 경로 추적이 가능하고 세밀한 설정이 가능

> ### ex
>
> 1단계: 계약서에서조항별텍스트를표로추출하라.
>
> 2단계: 추출된각조항을리스크유형별로분류하라.
>
> 3단계: 분류된리스크에근거와함께요약리포트를작성하라.
>
> (각 단계 출력이 다음 단계의 입력이 됨)

**> 평가: 1.프롬프트가 실제로 2개 이상 단계로 분리됐는가. 2. 각 단계의 입출력이 표시 정의됐는가. 3.단계를 나눈 이유가 명확한가.**

### 4.Memory & Compaction

길어지는 대화에서 무엇을 기억하고 요약할지 설계하는 기법

- 대화 내용의 우선 순위를 설정해서 근거를 설정하고 대응하게 지시함
- 모든 것을 텍스트에 넣기에는 부적합함
- 적합 케이스
  - 여러 턴에 걸친 상담 이력(헬프데스크)
  - 장기 세션으로 운영되는 분석 에이전트
  - 이전 이력이 이후 판단의 전제가 되는 모든 서비스
- 비적합 케이스
  - 1회성 단발 질문에는 불필요
  - 무엇을 압축할지 잘못 판단하면 핵심 정보를 잃어버림
  - *긴 대화일수록 정보 유실 여부를 직접 테스트해야함*

> ### ex
>
> 대화가 길어지면 다음정보는 반드시 유지하세요.
> · 고객플랜/구독료· 미처리요청· 최근담당자명· 최근크레딧 이력
> 그 외 단순 인사 및 일반 안내는 한 줄로 요약해도 됩니다.

**> 평가 : 1. 무엇을 기억할지 명시했는가. 2. 긴 대화 테스트에서 초반 정보를 끝까지 유지했는가. 3. 압축 과정에서 핵심 정보 손실이 없는가?**
