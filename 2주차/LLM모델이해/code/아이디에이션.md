> 한 줄 정의: 고장이력과 이용객 흐름을 분석해 에스컬레이터의 점검 종류를 정하고, 2인 1조·3교대 인력을 배치하는 AI 예방점검 서비스

> 핵심 메시지: 모든 시설을 같은 방식으로 점검하지 않고, 현재 이상·계절 위험·기계 관리 목적에 따라 점검 방법과 담당 인력을 다르게 제안한다.

## 1. Biz 가치

### 슬라이드 2. 배경과 문제

**문제에 공감한 계기**

- 대중교통 출퇴근 중 에스컬레이터 점검과 운행 중단으로 불편을 경험했다.
- 출퇴근 시간의 고장은 이동 지연과 통로 혼잡으로 확대된다.
- 같은 시설도 현재 이상 여부, 계절, 설치 환경에 따라 필요한 점검이 다르다.

**현장 담당자의 어려움**

- 과거 고장이력과 현재 이상 신호를 함께 확인해야 한다.
- 장마·해빙기에는 평소와 다른 취약 부분을 먼저 살펴야 한다.
- 점검 종류별 수행 주체와 필요한 자격이 다르다.
- 긴급상황이 발생하면 기존 일정과 근무조를 다시 조정해야 한다.
- 작업자의 지역, 경험, 교대, 피로도와 이동시간을 동시에 고려하기 어렵다.

**핵심 문제**

> 제한된 인력으로 어떤 시설을, 어떤 점검으로, 언제, 누가 확인할지 빠르게 정하기 어렵다.

### 슬라이드 3. 세 가지 점검 체계

| 점검 종류    | 언제 필요한가                                                  | 목적                         | 수행 주체                                   | 주요 확인 내용                             |
| ------------ | -------------------------------------------------------------- | ---------------------------- | ------------------------------------------- | ------------------------------------------ |
| 긴급점검     | 실시간 이상, 운행 중지, 최근 반복고장 등 즉시 대응이 필요할 때 | 현재 이상에 빠르게 대응      | 현재 교대의 현장 점검조                     | 이상 신호와 반복고장 부분, 안전 관련 항목  |
| 수시특별점검 | 해빙기·장마철처럼 특정 시기와 취약 환경이 겹칠 때             | 계절 위험을 미리 보완        | 정부·지자체 합동점검단 또는 자체 관리 주체 | 구조물 뒤틀림, 배수펌프, 차수판, 누전 위험 |
| 자체점검     | 정해진 점검일이 되었거나 소모품·성능 관리가 필요할 때         | 오작동 예방과 기계 성능 유지 | 유지관리 자격을 갖춘 전문 기술자            | 윤활, 브레이크 마모, 볼트 풀림, 센서 작동  |

**분류가 겹칠 때의 기준**

```text
긴급점검 > 수시특별점검 > 자체점검
```

- 현재 이상 대응을 가장 먼저 처리한다.
- 긴급하지 않으면 계절·환경 조건을 확인한다.
- 두 조건에 해당하지 않으면 자체점검 기한과 기계 상태를 확인한다.
- AI가 후보를 제시하고 최종 점검 결정은 현장 책임자가 승인한다.

### 슬라이드 4. 서비스가 해결하는 일

1. 고장이력에서 반복고장과 최근 재발을 찾는다.
2. 현재 상태와 실시간 이상 여부를 확인한다.
3. 이용객이 많은 시간과 점검하기 좋은 시간을 구분한다.
4. 기준일 다음 달의 계획월·계절·시설 환경과 자체점검 예정일을 확인한다.
5. 시설을 긴급·수시특별·자체점검 중 하나로 분류한다.
6. 다음 달의 실제 날짜를 `YYYY-MM-DD`로 정하고 같은 소속조의 2명, 근무 교대와 자격을 확인한다.
7. 점검이 있는 날짜마다 주간·석간·야간별 긴급대기조를 남긴다.

| 기존 방식                          | STEP GUARD 적용 후                         |
| ---------------------------------- | ------------------------------------------ |
| 점검 종류를 담당자가 자료별로 판단 | 세 가지 점검 후보와 근거를 한 번에 확인    |
| 고장정보와 이용객 정보가 분리      | 기계 위험과 이용객 불편을 역할별로 분석    |
| 긴급상황마다 근무표를 수작업 조정  | 교대·피로도·지역을 반영한 일정 초안 생성 |
| 판단 근거가 개인 경험에 집중       | 시설별 분류 이유와 확인사항을 함께 제공    |

**서비스가 하지 않는 일**

- 정확한 고장 날짜나 실제 고장 확률을 예측하지 않는다.
- AI가 안전 여부나 작업 가능 여부를 최종 승인하지 않는다.
- 입력에 없는 작업자 상태나 시설 정보를 만들어내지 않는다.

## 2. 에이전트 설정

### 슬라이드 6. Agent 역할

| Agent                      | 담당 질문                      | 사용하는 정보                                    | 핵심 결과                                            |
| -------------------------- | ------------------------------ | ------------------------------------------------ | ---------------------------------------------------- |
| 기계 고장 분석 담당자      | 왜 점검해야 하는가?            | 시설정보, 고장이력, 현재 상태와 환경             | 위험등급, 반복고장, 확인할 기계 부분                 |
| 이용객 패턴 분석 담당자    | 언제 점검하면 불편이 적은가?   | 역·요일·시간대별 이용객과 혼잡도               | 혼잡시간, 추천·비추천 시간                          |
| 점검 종류·우선순위 담당자 | 어떤 점검을 먼저 해야 하는가?  | 앞선 두 결과, 실시간 이상, 계절 기준, 자체점검일 | 3종 점검 분류, 우선순위, 완료기한                    |
| 현장 일정 관리자           | 다음 달 언제, 누가 점검하는가? | 분류 결과, 작업자 13개 칼럼, 운영규칙            | 실제 날짜의 점~~ㄱ~~ 일정과 날짜·교대별 인력운영안 |

**역할을 분리한 이유**

- 이용객이 많다는 이유만으로 기계 고장 위험이 높다고 판단하지 않는다.
- 기계 Agent는 시설만 보고, 이용객 Agent는 사람의 이동만 본다.
- 점검 분류 Agent가 두 분석과 계절·점검기한을 처음으로 합친다.
- 일정 Agent는 고장 원인을 새로 추측하지 않고 배정 가능성만 판단한다.

> 기계 Agent는 ‘왜’, 이용객 Agent는 ‘언제’, 분류 Agent는 ‘어떤 점검부터’, 일정 Agent는 ‘누가’를 답한다.

### 슬라이드 7. Agent 간 결과 전달

```text
시설정보 + 고장이력
        ↓
[기계 고장 분석]
위험등급·반복고장·중점점검항목 ─────────┐
                                           ↓
이용객패턴 → [이용객 분석] → 추천·비추천시간 → [점검 분류]
                                           ↑
        실시간 이상 + 특별점검 기준 + 자체점검 예정일
                                           ↓
                   긴급·수시특별·자체점검 목록
                                           ↓
작업자정보 + 운영규칙 → [현장 일정 관리]
                                           ↓
다음 달 YYYY-MM-DD 일정 3종 + 날짜·교대별 긴급대기조
```

**Agent별 생각 과정**

1. 기계 Agent: 최근 고장 → 같은 고장 반복 → 조치 후 재발 → 현재 이상 → 확인할 부분 순서로 본다.
2. 이용객 Agent: 역과 요일 연결 → 시간대 비교 → 혼잡시간 제외 → 이용객이 적은 시간 추천 순서로 본다.
3. 분류 Agent: 긴급 조건 → 다음 달의 계절 특별조건 → 자체점검 조건 → 같은 등급 안에서 이용객 영향 순서로 본다.
4. 일정 Agent: 다음 달 날짜 → 가능한 요일·교대 → 같은 소속조 2명 → 지역·경험·자격 → 피로도·이동시간 → 교대별 대기조 순서로 본다.

**공통 규칙**

- 제공된 데이터만 사용한다.
- 정보가 없으면 `추가 확인 필요`라고 표시한다.
- 점검 종류는 시설별로 하나만 선택한다.
- 실제 안전 판단과 일정 승인은 사람에게 남긴다.

**Agent별 실제 입력 칼럼**

| Agent               | 직접 전달하는 데이터                                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 기계 고장 분석      | 시설ID, 설치연도, 마지막점검일, 현재상태, 실시간이상여부, 최근이상감지시각, 실내외, 최근환경 + 고장이력 5개 칼럼        |
| 이용객 패턴 분석    | 시설ID, 역명, 위치, 대체이동수단 + 이용객패턴 6개 칼럼                                                                  |
| 점검 종류·우선순위 | 시설ID, 역명, 다음자체점검예정일, 현재상태, 실시간이상여부, 최근이상감지시각, 실내외, 최근환경 + 특별점검 기준 6개 칼럼 |
| 현장 일정 관리      | 작업자정보 13개 칼럼 + 현장운영규칙 2개 칼럼 + 앞선 Agent 결과                                                          |

> 시설정보 전체를 모든 Agent에게 주지 않는다. 코드가 Agent별 전용 데이터 표를 만든 뒤 Task에서 언급한 칼럼만 전달한다.

**작업자 운영 조건**

- 작업자 35명
- 고정 2인 1조 17개 조와 대체인력 1명
- 주간 6개 조, 석간 6개 조, 야간 5개 조
- 주간·석간·야간 각 교대에서 최소 1개 조를 긴급대기로 확보
- 피로도가 높은 작업자에게 긴급점검을 연속 배정하지 않음
- 다른 역 작업 사이 30분 이동시간 확보

**작은 데이터로 시작할 수 있는 이유**

- 별도 모델 학습 없이 표 형식 데이터를 프롬프트에 전달한다.
- 각 Agent가 맡은 칼럼만 보고 역할 범위를 지킨다.
- 결과를 CSV로 저장해 사람이 검토하고 수정할 수 있다.
- CSV 필수 칼럼이 빠지면 Agent 실행 전에 코드가 오류를 표시한다.

**월간 일정 생성 규칙**

- 기준일이 `2026-07-24`이면 계획월은 자동으로 `2026-08`이 된다.
- 점검일과 운영일은 `2026-08-01`부터 `2026-08-31` 사이의 실제 날짜로 작성한다.
- `월·화·수` 같은 요일 문자가 아니라 `YYYY-MM-DD`를 결과에 저장한다.
- 작업자의 `가능일` 요일과 실제 달력 날짜의 요일이 일치해야 한다.

**코드로 확인하는 항목**

- 모든 시설이 세 종류 중 하나에 배정됐는가?
- 같은 시설이 중복 배정됐는가?

- 입력 CSV에 Task가 요구하는 모든 칼럼이 존재하는가?
- 점검일과 운영일이 `YYYY-MM-DD`이며 다음 달 범위 안에 있는가?
- 점검이 있는 날짜마다 주간·석간·야간 인력운영 행이 모두 있는가?
- 각 교대에 실제 긴급대기조 코드가 있는가?

**사람이 확인하는 항목**

- 분류 근거가 입력 데이터와 일치하는가?
- 수시특별점검의 시기·환경·수행 주체가 타당한가?
- 자체점검 조에 유지관리 자격자가 포함됐는가?
- 교대, 지역, 경험, 피로도와 이동시간이 현실적인가?
- 교대별 긴급대기조를 실제로 운영할 수 있는가?

**현재 검증 상태**

- `실습3.ipynb`의 Agent, 데이터 연결, 3종 분류, 일정 생성과 CSV 저장 코드를 구현했다.
- 노트북 JSON과 Python 문법, CSV 구조, 35명·17개 조 편성을 확인했다.
- Agent별 Task와 전용 입력 칼럼, 51개 칼럼 매핑의 일치를 확인했다.
- 기준일 다음 달 계산 결과가 `2026-08-01~2026-08-31`인지 검증했다.
- 기존 실행 결과는 제거했으며 실제 API 실행 결과는 별도 검증이 필요하다.
- 따라서 발표에서는 구현 결과와 현장 성능을 구분해 설명한다.
