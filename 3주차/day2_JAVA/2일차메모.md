# 2일차 Configuration과Profile 관리

## Configuration, Profile이란

> App 실행 시 필요한 환경 정보 (포트, DB, API )를 코드가 아닌 외부 파일 또는 환경변수로 분리해 관리함을 의미 즉, 코드를 수정하지 않고 **환경에 따라** 설정만 바뀌어 APP 실행 가능토록 함

## 개발된 이유

> 기존 방식에서는 개발 운영마다 환경이 달라서 DB 세팅하는 방법이 다름
> 설정 정보를 코드 밖(yml, 환경 변수)으로 추출해두면 설정 따라 받으면 됨

- Configuration은 설정을 **외부화하는 개념**
  - 어떤 설정값을 설정할지 정의 (DB는 포스트그래스로 주소는 이걸로 합시다!)
- Profile은 외부화된 설정을 실행 환경별로 구분하고 선택하는 **기능**입니다.
  - 여러 설정(DB,Key)를 개발,유저 등 환경에 맞춰서 **따로따로(8080,9090,1010)** 으로 설정합시다!

## 데이터 값 취합하는 어노테이션 종류 (그닥 안쓰임)

### `@ConfigurationProperties`

- 기능: 공통 접두사를 가진 여러 설정값을 하나의 객체로 묶어 주입
- 목적: 설정값을 타입 안전하고 체계적으로 관리
- 특징:
  - 설정이 많을 때 적합
  - YAML의 계층 구조를 객체로 표현 가능
  - 타입 변환과 유효성 검증 지원
  - Spring Bean으로 등록해야 사용 가능

```yaml
app:
  name: my-service
  timeout: 30
```

```java
@ConfigurationProperties(prefix = "app")
public record AppProperties(
    String name,
    int timeout
) {}
```

등록 방법:

```java
@ConfigurationPropertiesScan
@SpringBootApplication
public class Application {
}
```

---

### `@Value`

- 기능: 설정값 하나를 특정 필드나 생성자 매개변수에 주입
- 목적: 소수의 간단한 설정값을 개별적으로 사용
- 특징:
  - `${키:기본값}` 형태로 사용
  - 기본값 지정 가능
  - SpEL 표현식 사용 가능
  - 설정값이 많아지면 관리하기 어려움
  - `@ConfigurationProperties`보다 타입 안전성과 구조화가 부족함

```java
@Value("${app.name:default-app}")
private String appName;
```

> `@Value`는 여러 설정을 하나의 객체로 묶는 기능이 아니라, 설정값을 **개별적으로 주입**하는 기능이다.

## 검증 어노테이션

- 개념: 입력값이나 설정값이 지정된 규칙에 맞는지 확인하는 기능
- 목적: 잘못된 설정으로 애플리케이션이 실행되는 것을 방지
- 의존성:

```gradle
implementation 'org.springframework.boot:spring-boot-starter-validation'
```

`@ConfigurationProperties`를 검증하려면 `@Validated`를 추가한다.

```java
@Validated
@ConfigurationProperties(prefix = "mail")
public record MailProperties(
    @NotBlank String host,
    @Min(1) @Max(65535) int port,
    @Email String sender
) {}
```

### 주요 검증 어노테이션

- `@NotNull`: 값이 `null`이면 안 됨
- `@NotBlank`: 문자열이 `null`, 빈 문자열 또는 공백이면 안 됨
- `@NotEmpty`: 문자열이나 컬렉션이 `null` 또는 비어 있으면 안 됨
- `@Size`: 문자열·컬렉션 등의 크기 제한
- `@Email`: 이메일 형식 검사
- `@Pattern`: 정규 표현식 검사
- `@Min`, `@Max`: 숫자의 최솟값·최댓값 검사
- `@Positive`: 양수인지 검사

> 어노테이션 이름은 대소문자를 구분하므로 `@Notnull`이 아니라 `@NotNull`이다.

## Spring MVC

> Spring MVC는 **웹 요청을 Controller가 처리하고 결과를 View 또는 JSON으로 반환하는 Spring의 웹 프레임워크**이다. MVC는 Model, View, Controller의 약자다.

### 특징

- MVC 패턴으로 역할을 분리
- 어노테이션 기반 요청 처리
- URL과 HTTP 메서드를 Controller에 매핑
- 요청 데이터 자동 변환 및 검증 지원
- 예외를 공통으로 처리할 수 있

### 주요 컴포넌트

![1785284904348](/Users/chltmddn5843/Downloads/skala/3주차/day2_JAVA/2일차메모/1785284904348.png)

```text
DispatcherServlet
├── HandlerMapping
├── HandlerAdapter
	├── Controller
    	├── Model
		├── Service
        	├── Repository
├── ViewResolver
└── View
```

- `DispatcherServlet`: 모든 요청을 가장 먼저 받는 중앙 컨트롤러
- `HandlerMapping`: 요청을 처리할 Controller 메서드를 검색
- `HandlerAdapter`: 검색된 Controller 메서드를 실행
- `Controller`: 요청을 받고 응답을 결정
- `Model`: View에 전달할 데이터
- `ViewResolver`: View 이름에 해당하는 실제 화면 파일 검색
- `View`: HTML 화면 생성
- `HttpMessageConverter`: 객체와 JSON을 서로 변환
- `Service`: 비즈니스 로직 처리
- `Repository`: 데이터베이스 접근

### 주요 처리

### HTML을 반환하는 경우

```text
클라이언트 요청
    ↓
DispatcherServlet
    ↓
HandlerMapping
    ↓
HandlerAdapter
    ↓
Controller → Service → Repository
    ↓
Model + View 이름
    ↓
ViewResolver
    ↓
View 렌더링
    ↓
HTML 응답
```

### JSON을 반환하는 경우

```text
클라이언트 요청
    ↓
DispatcherServlet
    ↓
Controller
    ↓
Service → Repository
    ↓
반환 객체
    ↓
HttpMessageConverter
    ↓
JSON 응답
```

## DispatcherServlet

> Spring MVC의 **모든 HTTP 요청을 가장 먼저 받아 적절한 Controller로 전달하는 중앙 서블릿**이다. Front Controller라고도 한다.

```text
클라이언트 요청
    ↓
DispatcherServlet
    ↓
HandlerMapping으로 Controller 검색
    ↓
HandlerAdapter로 Controller 실행
    ↓
HTML 또는 JSON 응답
```

Spring Boot에서는 `DispatcherServlet`이 자동으로 등록되므로 일반적으로 직접 설정할 필요가 없다.

### 의존성 설치

### Gradle

```gradle
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
}
```

### Maven

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

`spring-boot-starter-web`에는 Spring MVC, 내장 Tomcat, JSON 변환을 위한 Jackson 등이 포함된다.

### 기본 사용 예시

## Controller

### 개념

HTTP 요청을 받아 요청값을 해석하고, Service를 호출한 뒤 결과를 반환하는 계층이다.

### 종류

- `@Controller`: 주로 View 이름을 반환
- `@RestController`: 객체를 JSON으로 반환
- `@RestController` = `@Controller` + `@ResponseBody`

```java
@RestController
@RequestMapping("/users")
public class UserController {
}
```

### `@RequestMapping`

Controller나 메서드에 **공통 URL과 HTTP 메서드를 연결**한다.

```java
@RequestMapping("/users")
```

```java
@RequestMapping(value = "/list", method = RequestMethod.GET)
public List<User> getUsers() {
    return users;
}
```

일반적으로 HTTP 메서드별 전용 어노테이션을 더 많이 사용한다.

- `@GetMapping`: 조회
- `@PostMapping`: 생성
- `@PutMapping`: 전체 수정
- `@PatchMapping`: 일부 수정
- `@DeleteMapping`: 삭제

### `@RequestParam`

URL의 **쿼리 파라미터** 또는 폼 데이터를 매개변수로 받는다.

```java
@GetMapping
public String search(
    @RequestParam String keyword,
    @RequestParam(defaultValue = "1") int page
) {
    return keyword + ", " + page;
}
```

요청 예시:

```http
GET /users?keyword=kim&page=2
```

주요 옵션:

- `required`: 필수 여부이며 기본값은 `true`
- `defaultValue`: 값이 없을 때 사용할 기본값
- `name` 또는 `value`: 요청 파라미터 이름 지정

```java
@RequestParam(name = "keyword", required = false)
String keyword
```

### `@PathVariable`

URL 경로에 포함된 값을 매개변수로 받는다. 주로 특정 자원을 식별할 때 사용한다.

```java
@GetMapping("/{id}")
public String getUser(@PathVariable Long id) {
    return "사용자 번호: " + id;
}
```

요청 예시:

```http
GET /users/10
```

이때 `id`에는 `10`이 전달된다.

```text

@PathVariable → /users/10         특정 자원 식별
```

## Model

### 개념

> 데이터를 **저장하고 전달하는 객체
> 컨트롤러가 비즈니스 로직을 수행한 결과를 View로 전달하는 중간 매개체**

### 종류

- ModelMap
- ModelAndView
- @ModelAttribute

### 역할

- spring이 자동 관리
- 데이터 전달 (컨트롤러가 뷰에 데이터를 전달할 수 있게 함)
- key/value 구조 (model.addAttribute : key, value형태)
- 스코프 관리 (request 범위 내에서 유효하게함)

### 구조

MVC의 Model 영역
├── DTO/Entity: 데이터 구조
├── Service: 비즈니스 로직
└── Repository: 데이터 저장·조회

> 사용자
> ↓
> Controller
> ↓
> Service
> ↓
> Repository
> ↓
> DB

**Spring IoC 컨테이너가 이 객체들을 Bean으로 생성·관리함**

## Service

### 개념

> Model의 종류 중 하나로 레퍼지토리와 연결하여 비즈니스 로직을 처리하는 계층이다.

```text
Controller → Service → Repository
```

예를 들면 상품 등록 시 다음 작업을 담당합니다.

- 상품명이 비어 있는지 검사
- 가격이 음수인지 검사
- 할인 가격 계산
- 재고 확인
- Repository에 저장 요청

---

### 역할

| 계층       | 역할                           |
| ---------- | ------------------------------ |
| Controller | HTTP 요청과 응답 처리          |
| Service    | 업무 절차와 비즈니스 규칙 처리 |
| Repository | 데이터 저장·조회              |
| View       | 결과 화면 출력                 |

Controller가 직접 데이터를 처리하지 않고 Service에 요청합니다.

```java
@PostMapping
public String create(@ModelAttribute Item item) {
    service.create(item);
    return "redirect:/items";
}
```

---

### 주요 기능

Service에서는 일반적으로 다음 기능을 수행합니다.

- 데이터 검증
- 계산 및 데이터 가공
- 여러 Repository 작업 조합
- 등록·조회·수정·삭제 절차 관리
- 트랜잭션 관리
- 예외 발생 및 처리

```java
public Item create(Item item) {
    if (item.getPrice() < 0) {
        throw new IllegalArgumentException("가격은 음수일 수 없습니다.");
    }

    return repository.save(item);
}
```

---

### 주요 어노테이션

#### `@Service`

해당 클래스를 Service 계층의 Spring Bean으로 등록합니다.

```java
@Service
public class ItemServiceImpl {
}
```

Spring이 객체를 생성하고 필요한 곳에 주입해 줍니다.

#### `@Transactional`

여러 DB 작업을 하나의 작업 단위로 묶습니다.

```java
@Transactional
public void order(Item item) {
    repository.save(item);
    stockRepository.decrease(item.getId());
}
```

중간에 오류가 발생하면 이전 DB 작업도 취소할 수 있습니다.

조회 기능에는 다음과 같이 사용할 수 있습니다.

```java
@Transactional(readOnly = true)
public Item get(Long id) {
    return repository.findById(id);
}
```

#### `@Validated`

Service 메서드의 매개변수를 검증할 때 사용합니다.

```java
@Service
@Validated
public class ItemService {

    public Item get(@Positive Long id) {
        return repository.findById(id);
    }
}
```

---

### 5. 인터페이스와 구현 클래스

현재 프로젝트는 Service를 역할과 구현으로 나눕니다.

```java
public interface ItemService {
    List<Item> list();
    Item get(Long id);
    Item create(Item item);
    void update(Long id, Item item);
    void delete(Long id);
}
```

구현 클래스:

```java
@Service
public class ItemServiceImpl implements ItemService {

    private final ItemRepository repository;

    public ItemServiceImpl(ItemRepository repository) {
        this.repository = repository;
    }
}
```

- `ItemService`: 어떤 기능을 제공할지 정의
- `ItemServiceImpl`: 그 기능을 실제로 구현
- `implements`: 인터페이스의 약속을 구현한다는 의미

---

### 6. 의존성 주입

Service는 Repository를 직접 생성하지 않고 생성자로 전달받습니다.

```java
private final ItemRepository repository;

public ItemServiceImpl(ItemRepository repository) {
    this.repository = repository;
}
```

다음처럼 직접 생성하지 않습니다.

```java
// 권장하지 않음
ItemRepository repository = new InMemoryItemRepository();
```

Spring이 적절한 Repository Bean을 찾아 주입합니다. 이를 DI라고 합니다.

---

### 7. Service에 넣지 않는 것

Service에는 다음 내용을 가급적 넣지 않습니다.

- URL 설정: Controller
- HTML 화면 선택: Controller
- HTTP 요청·응답 직접 처리: Controller
- SQL 또는 데이터 저장 세부 구현: Repository
- 화면 디자인: View

---

### 한 문장 정리

> Service는 Controller의 요청을 받아 비즈니스 규칙을 처리하고, Repository를 이용해 데이터를 저장하거나 조회하는 Spring Bean입니다.

## Repository

### 1. 개념

Repository는 데이터의 저장, 조회, 수정, 삭제를 담당하는 계층입다.

```text
Controller → Service → Repository → DB
```

Service는 “어떤 업무를 처리할지” 결정하고, Repository는 “데이터를 어떻게 저장하고 가져올지” 담당합니다.

---

### 2. 주요 역할

- 데이터 저장
- 전체·개별 데이터 조회
- 데이터 수정
- 데이터 삭제
- ID나 이름을 이용한 데이터 검색
- DB 또는 메모리 저장소 접근

CRUD와 연결하면 다음과 같습니다.

| 기능         | Repository 메서드 예시          |
| ------------ | ------------------------------- |
| 생성(Create) | `save(item)`                  |
| 조회(Read)   | `findAll()`, `findById(id)` |
| 수정(Update) | `update(id, item)`            |
| 삭제(Delete) | `delete(id)`                  |

---

### 3. 현재 프로젝트 구조

```text
ItemRepository
        ↑
InMemoryItemRepository
```

`ItemRepository`는 기능을 정의하는 인터페이스입니다.

```java
public interface ItemRepository {
    List<Item> findAll();

    Item findById(Long id);

    Item save(Item item);

    void update(Long id, Item item);

    void delete(Long id);
}
```

`InMemoryItemRepository`는 해당 기능을 메모리 저장소로 구현합니다.

```java
@Repository
public class InMemoryItemRepository implements ItemRepository {

    private final Map<Long, Item> store = new HashMap<>();
}
```

현재는 DB 대신 `Map`에 데이터를 저장하므로 애플리케이션을 종료하면 데이터가 사라집니다.

---

### 4. 주요 어노테이션

#### `@Repository`

클래스를 Repository 역할의 Spring Bean으로 등록합니다.

```java
@Repository
public class InMemoryItemRepository {
}
```

주요 효과:

- Spring Bean으로 등록
- 생성자 주입 대상이 됨
- DB 관련 예외를 Spring의 데이터 접근 예외로 변환

#### `@Transactional`

Repository보다 일반적으로 Service에 사용합니다.

```java
@Transactional
public void create(Item item) {
    repository.save(item);
}
```

여러 데이터 작업을 하나의 단위로 처리합니다.

Spring Data JPA를 사용하면 다음 어노테이션도 접하게 됩니다.

- `@Query`: 직접 JPQL/SQL 쿼리 정의
- `@Modifying`: 수정·삭제 쿼리 표시
- `@Param`: 쿼리 매개변수 연결

---

### 5. Service와의 차이

| 구분            | Service              | Repository      |
| --------------- | -------------------- | --------------- |
| 주요 책임       | 업무 규칙 처리       | 데이터 접근     |
| 예시            | 가격 검증, 할인 계산 | 상품 저장·조회 |
| 다음 계층       | Repository 호출      | DB 접근         |
| 주요 어노테이션 | `@Service`         | `@Repository` |

예시:

```java
@Service
public class ItemServiceImpl {

    private final ItemRepository repository;

    public Item create(Item item) {
        if (item.getPrice() < 0) {
            throw new IllegalArgumentException("가격 오류");
        }

        return repository.save(item);
    }
}
```

- 가격 검사: Service의 역할
- 상품 저장: Repository의 역할

---

### 6. Repository를 분리하는 이유

저장 방식을 변경해도 Service의 변경을 줄일 수 있습니다.

```text
ItemRepository
├── InMemoryItemRepository
├── JdbcItemRepository
└── JpaItemRepository
```

Service는 구체적인 구현체가 아닌 `ItemRepository` 인터페이스에 의존합니다.

```java
private final ItemRepository repository;
```

따라서 메모리 저장소를 MySQL이나 JPA로 변경해도 Service의 업무 로직을 그대로 유지할 수 있습니다.

> Repository는 데이터 저장소에 접근하여 CRUD를 수행하고, 그 구현 방법을 Service로부터 숨기는 계층입니다.

# 핵심

MVC                         Spring 계층형 구조

Controller  ──────────────→ Controller
Model       ──────────────→ Service + Repository + DTO/Entity
View        ──────────────→ Thymeleaf/HTML

```java
@RestController
@RequestMapping("/users")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/{id}")
    public UserResponse getUser(@PathVariable Long id) {
        return userService.findById(id);
    }
}
```
