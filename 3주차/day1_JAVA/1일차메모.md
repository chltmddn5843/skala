# 객체지향 프로그래밍

## 절차적 프로그래밍(PP) vs 객체 지향 프로그램 (OOP)

### 특징 차이

- 절차적 프로그래밍 : 순차, 조건 ,반복
- 객체 지향 프로그래밍 : 캡슐화, 추상화, 다형성, 상속

### 객프 특징 설명

1. 추상화 (Abstraction)

   * 개념: 복잡한 현실 세계의 대상에서 **공통적이고 핵심적인 특징**만 추출하여 모델링하는 과정
   * 백엔드 예시: 고객 관리 시스템을 만들 때 사람의 키, 몸무게, 시력 등은 제외하고, 백엔드 로직에 필요한 고객ID, 이메일, 결제수단 등 핵심 정보와 기능만 클래스로 정의하는 것입니다.
     * 자식 상속을 위해서임
2. 캡슐화 (Encapsulation)

   * 개념: 데이터(속성)와 해당 데이터를 다루는 기능(메서드)을 하나로 묶고, 외부에서의 직접적인 접근을 제한하여 보호하기
   * 백엔드 예시: 사용자의 비밀번호 변수를 외부에서 직접 수정하지 못하게 private으로 막아두고, 검증 로직을 거치는 메서드(e.g., changePassword())를 통해서만 변경할 수 있도록 안전장치를 마련합니다.
3. 상속 (Inheritance)

   * 개념: 상위 클래스(부모)의 자원(필드, 메서드)을 하위 클래스(자식)가 물려받아 재사용하거나 확장하는 것입니다.
   * 백엔드 예시: 공통 유저 클래스(User)를 정의하고, 이를 상속받아 일반 회원(Member)과 관리자(Admin) 클래스를 만들어 중복 코드를 극적으로 줄입니다.
4. 다형성 (Polymorphism) ★★★ (Spring의 핵심)

   - 개념: 하나의 타입이나 메서드가 상황에 따라 여러 가지 다양한 형태/동작으로 변신하는 성질입니다. (오버라이딩, 역할과 구현의 분리)
   - 백엔드 예시: 결제(Payment)라는 역할(인터페이스)을 정의해 두면, 실제 구현체가 카카오페이결제, 신용카드결제, 토스페이결제 등 무엇이 들어오든 동일한 인터페이스로 처리할 수 있습니다.

## SOLID 원칙

![1785115177861](image/메모/1785115177861.png)

## 📌 SOLID 5대 원칙 요약

1. SRP (단일 책임 원칙, Single Responsibility Principle)

   * 개념: 하나의 클래스는 단 하나의 책임(변경 이유)만 가져야 한다.
   * 백엔드 예시: Controller(요청 처리), Service(비즈니스 로직), Repository(DB 접근)로 계층을 분리하여 구현한다.
2. OCP (개방-폐쇄 원칙, Open/Closed Principle)

   * 개념: 기능 확장에는 열려(Open) 있어야 하고, 기존 코드 수정에는 닫혀(Closed) 있어야 한다.
   * 백엔드 예시: Payment 인터페이스를 정의한 후 카카오페이, 네이버페이 등 결제 수단을 추가할 때 기존 로직 변경 없이 클래스만 추가한다.
3. LSP (리스코프 치환 원칙, Liskov Substitution Principle)

   * 개념: 하위 타입(자식 클래스)은 언제나 상위 타입(부모 인터페이스)을 대체할 수 있어야 한다.
   * 백엔드 예시: 인터페이스에 정의된 동작 약속(규약)을 자식 구현체가 깨뜨리지 않고 올바르게 동작해야 한다.
4. ISP (인터페이스 분리 원칙, Interface Segregation Principle)

   * 개념: 사용하지 않는 메서드에 의존하지 않도록 인터페이스를 작고 명확하게 분리해야 한다.
   * 백엔드 예시: 하나의 거대한 인터페이스보다 기능별로 쪼개진 여러 인터페이스를 작성하여 불필요한 메서드 구현을 방지한다.
5. DIP (의존역전 원칙, Dependency Inversion Principle) -???

   - 개념: 구체적인 구현 클래스가 아닌, 추상화(인터페이스)에 의존해야 한다.
   - 백엔드 예시: OrderService가 특정 결제 구현체 클래스를 직접 생성하지 않고 PaymentClient 인터페이스에만 의존하며, Spring이 외부에서 객체를 주입(DI)해준다.

## 생성자 주입

```java
public UserService(UserRepository userRepository) {
    this.userRepository = userRepository;
}
```

먼저 아래 필드가 있다고 가정합니다.

```java
@Service
public class UserService {

    // UserService가 데이터 조회에 사용할 Repository입니다.
    // final: 생성된 후 다른 Repository로 재할당하지 못하게 합니다.
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        // 왼쪽: UserService의 필드
        // 오른쪽: 생성자로 전달받은 객체
        this.userRepository = userRepository;
    }
}
```

## 생성자가 하는 일

`this.userRepository`와 `userRepository`는 이름은 같지만 서로 다릅니다.

```java
this.userRepository = userRepository;
```

- `this.userRepository`: 현재 `UserService` 객체의 필드
- `userRepository`: 생성자로 전달받은 매개변수
- `this`: 현재 객체 자신

쉽게 표현하면:

> Spring이 준비한 Repository를 UserService 내부에 보관한다.

Spring이 실제로는 다음과 비슷한 일을 해줍니다.

```java
UserRepository repository = /* Spring이 생성한 Repository 객체 */;
UserService service = new UserService(repository);
```

개발자가 직접 `new`로 만들지 않아도 `@Service`, `@Repository` 등을 보고 Spring이 연결합니다.

## 왜 필요한가?

Service는 데이터베이스에서 사용자를 조회하기 위해 Repository가 필요합니다.

```java
User user = userRepository.findById(id);
```

그런데 생성자를 통해 Repository를 전달받지 않으면 `userRepository`에 사용할 객체가 없습니다.

```java
private final UserRepository userRepository;
```

`final` 필드는 반드시 생성 과정에서 값을 넣어야 하므로 생성자가 필요합니다.

```java
public UserService(UserRepository userRepository) {
    this.userRepository = userRepository;
}
```

이 생성자가 있기 때문에 이후 모든 Service 메서드에서 다음과 같이 사용할 수 있습니다.

```java
userRepository.findById(id);
userRepository.save(user);
userRepository.delete(user);
```

## `findById()` 부분에 미치는 영향

```java
public UserResponse findById(Long id) {
    User user = userRepository.findById(id);

    return new UserResponse(
            user.getId(),
            user.getName()
    );
}
```

처리 과정을 나누면 다음과 같습니다.

```java
// 1. Controller에서 받은 id를 사용해 Repository에 조회를 요청합니다.
User user = userRepository.findById(id);
```

```java
// 2. 조회한 Entity를 클라이언트 응답용 DTO로 변환합니다.
return new UserResponse(
        user.getId(),
        user.getName()
);
```

생성자에서 `userRepository`를 저장했기 때문에 `findById()` 메서드가 Repository를 사용할 수 있는 것입니다.

## Service의 `findById()` 이름은 임의인가?

다음 Service 메서드 이름은 **개발자가 목적에 맞게 정합니다.**

```java
public UserResponse findById(Long id)
```

다음처럼 다른 이름도 문법적으로 가능합니다.

```java
public UserResponse getUser(Long id)
public UserResponse searchUser(Long id)
public UserResponse findUserById(Long id)
```

하지만 협업과 가독성을 위해 동작이 분명한 이름을 사용합니다.

- `findById`: ID로 조회
- `findAll`: 전체 조회
- `createUser`: 사용자 생성
- `updateUser`: 사용자 수정
- `deleteUser`: 사용자 삭제

즉, 완전히 고정된 이름은 아니지만 **메서드가 하는 일을 드러내는 이름으로 정하는 관례**가 있습니다.

## Repository의 `findById()`는 조금 다름

Spring Data JPA를 사용한다면 Repository의 `findById()`는 기본 제공 메서드입니다.

```java
public interface UserRepository extends JpaRepository<User, Long> {
}
```

여기서:

```java
JpaRepository<User, Long>
```

- `User`: 이 Repository가 관리할 Entity
- `Long`: `User`의 ID 타입

`JpaRepository`가 다음 메서드들을 기본 제공합니다.

```java
findById(id);
findAll();
save(user);
delete(user);
```

따라서 Repository에 `findById()`를 직접 작성하지 않아도 됩니다.

실제 JPA의 `findById()` 반환 타입은 `User`가 아니라 `Optional<User>`입니다.

```java
@Service
public class UserService {

    private final UserRepository userRepository;

    // 생성자 주입: Spring이 만든 UserRepository를 전달받습니다.
    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public UserResponse findById(Long id) {

        // findById()는 사용자가 존재하지 않을 가능성이 있어서
        // Optional<User>를 반환합니다.
        User user = userRepository.findById(id)
                // 조회 결과가 없다면 예외를 발생시킵니다.
                .orElseThrow(() ->
                        new IllegalArgumentException("사용자가 없습니다: " + id)
                );

        // Entity를 외부 응답용 DTO로 변환합니다.
        return new UserResponse(
                user.getId(),
                user.getName()
        );
    }
}
```

## 이름으로 쿼리를 만드는 경우

Repository에 새로운 조회 조건을 만들 때는 Spring Data JPA의 명명 규칙을 사용할 수 있습니다.

```java
public interface UserRepository extends JpaRepository<User, Long> {

    // Spring이 메서드 이름을 분석해
    // "name이 같은 사용자를 조회하는 쿼리"를 만듭니다.
    List<User> findByName(String name);

    // 이메일이 같은 사용자 조회
    Optional<User> findByEmail(String email);
}
```

여기서는 이름이 완전히 임의적이지 않습니다.

- Service 메서드 이름: 개발자가 의미 있게 결정
- `JpaRepository`의 `findById`: Spring이 기본 제공
- Repository의 `findByName`: Spring Data JPA 명명 규칙을 따라 작성

핵심적으로 생성자는 **Repository를 Service에 연결**하고, Service의 `findById()`는 연결된 Repository를 이용해 **조회 → 가공 → 응답 DTO 반환**을 수행합니다.
