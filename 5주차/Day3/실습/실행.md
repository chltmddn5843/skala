# 인덱스 이외의 튜닝 실제 적용 결과

## 3. LIKE 접미사 검색 - 조건식 재작성

### 튜닝 방법

`LIKE '%@도메인'`을 `split_part(email, '@', 2) = '도메인'`으로 재작성했다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM hr.employees
WHERE split_part(email, '@', 2) = 'gmail.com';

EXPLAIN (ANALYZE, BUFFERS)
SELECT employee_id, first_name, last_name, email
FROM hr.employees
WHERE split_part(email, '@', 2) = 'outlook.com';
```

### 성능 비교

| 대상 | 기존 LIKE | split_part() | 결과 |
|---|---:|---:|---|
| gmail | 2.206ms | 2.363ms | 0.157ms 증가 |
| outlook | 2.119ms | 2.545ms | 0.426ms 증가 |

### 결론

`split_part()`는 행마다 함수를 계산하지만 Seq Scan을 제거하지 못해 오히려 느려졌다. 이 시도는 채택하지 않고, 반복되는 도메인 검색은 도메인 컬럼 정규화 또는 `reverse(email)` 표현식 인덱스를 검토한다.

## 4. ORDER BY + 필터 - 조회 컬럼 축소

### 튜닝 방법

`SELECT *`를 제거하고 화면에 필요한 컬럼만 조회하여 행 폭, 정렬 메모리, 전송량을 줄였다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT employee_id, email, hire_date, salary
FROM hr.employees
WHERE hire_date >= CURRENT_DATE - INTERVAL '365 days'
  AND status = 'ACTIVE'
ORDER BY salary DESC
LIMIT 100;
```

### 성능 비교

| 대상 | 광범위 컬럼 | 필요 컬럼 | 결과 |
|---|---:|---:|---|
| 실행 시간 | 5.304ms | 4.768ms | 약 10.1% 개선 |
| top-N 정렬 메모리 | 47kB | 36kB | 11kB 감소 |

### 결론

필요한 컬럼만 선택하는 방법은 실행 시간과 정렬 메모리를 줄였다. 다만 Seq Scan과 top-N Sort는 남아 있어 핵심 병목을 완전히 제거하는 방법은 아니다.

## 5. OR 조건 - 조건식 단순화와 UNION ALL 비교

### 튜닝 방법 1

연속된 정수인 `IN (3,4,5)`를 `BETWEEN 3 AND 5`로 단순화했다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM hr.employees
WHERE department_id = 10
   OR job_id BETWEEN 3 AND 5;
```

```text
Seq Scan on employees (actual time=0.004..3.848 rows=4085)
  Rows Removed by Filter: 45915
  Buffers: shared hit=786
Execution Time: 3.938 ms
```

### 튜닝 방법 2

OR를 상호 배타적인 `UNION ALL`로 분리해 중복 제거 연산을 없앰다.

```sql
SELECT * FROM hr.employees WHERE department_id = 10
UNION ALL
SELECT * FROM hr.employees
WHERE job_id IN (3,4,5)
  AND department_id <> 10;
```

### 성능 비교

| 비교 | 기존 | 재작성 | 결과 |
|---|---:|---:|---|
| 인덱스 없음: IN → BETWEEN | 5.658ms | 3.938ms | 단일 실행에서 개선 |
| 인덱스 있음: OR → 상호 배타 UNION ALL | 0.412ms | 0.563ms | UNION ALL이 느림 |

### 결론

`BETWEEN`은 단일 실행에서 시간이 감소했지만 Seq Scan은 제거되지 않았다. `UNION ALL`도 원본 `BitmapOr`보다 느렸으므로, 현재 데이터에서는 원본 OR와 각 컬럼 인덱스의 BitmapOr 계획이 가장 안정적이다.
